Module — Events & Death Messages

Events & Death Messages

Run any console or player command automatically when a Minecraft event fires — first join, kill, world change, PvP start, advancement, and 16 more. A separate, fully customisable death-message system replaces vanilla kill messages with rich, context-aware text that supports players, mobs, MythicMobs, and every environmental cause.

22 event typesFrom first join to elytra glide — hooks for everything.
3 directivesasConsole!, asPlayer!, delay! — run any command any way.
Death messagesFull priority chain: Player → MythicMobs → Mob → Environment.

What is the Events module?

The Events module is a command hook system. You list any number of server or player commands under each event type in events.yml. Whenever that event fires in-game, OreoEssentials automatically executes those commands — no scripting, no extra plugins needed.

Think of it like this: instead of writing a custom plugin every time you want to "give a player bread when they first join" or "broadcast a message when someone kills another player", you just add one line to a YAML file.

Alongside event hooks, the module also replaces vanilla death messages with richly customisable text stored in death-messages.yml. These support colour codes, PlaceholderAPI, multiple random variations, per-mob overrides, and full MythicMobs integration.

Both features together. The Events module handles all 22 event types and the death message system in the same place. Reloading with /oevents reload refreshes both files at once.

What can I do with it?

  • Give starter items to first-time players automatically
  • Add a custom welcome title/subtitle on join
  • Award money or points when a player kills another player
  • Notify a world channel when a player changes worlds
  • Run a LuckPerms command to add a group on first join
  • Announce when PvP combat begins and ends
  • Send a delayed message after respawn ("You have 30 seconds of protection…")
  • Show a completely custom, randomised death message for every cause of death
  • Display unique death messages for specific MythicMobs bosses
  • Broadcast death messages to all servers via RabbitMQ

Quick-start (4 steps)

1

Find your events.yml

The file is at plugins/OreoEssentials/chat-messaging/events.yml. Open it in any text editor. Every event type is already there, with example commands commented in.

2

Add a command to an event

Find the event you want (e.g. firstJoinServer:) and add a line using the correct directive. The most common is asConsole! <command>.

3

Use variables where needed

Replace player names or dynamic values with variables like [playerName], [victim], [level], etc. They are replaced automatically at runtime.

4

Reload and test

Run /oevents reload in-game or from console. Trigger the event (e.g. join with a new account) and verify the commands fired.

Tip: You do not need to restart the server. /oevents reload re-reads both events.yml and death-messages.yml live.

Config files

FilePurpose

Command directives explained

Every line you add under an event is a command entry. It starts with an optional directive that tells OreoEssentials how and when to run the command.

The three directives

DirectiveWhat it doesExample
asConsole! default Runs the command as the server console. Works for any command, including operator-only ones. This is the default — if you omit a directive, it behaves like asConsole!. asConsole! give [playerName] bread 8
asPlayer! player cmd Runs the command as the player who triggered the event. Useful for commands that check the sender's permissions or need the player's context. The player must still be online. asPlayer! home set spawn
delay! <seconds> timed Waits the given number of seconds before running the command. Can be combined with asConsole! or asPlayer! by prefixing the delay before or after them.
Note: the delay value is in whole seconds (not ticks). Internally converted to ticks (×20). 		asConsole! delay! 5 tell [playerName] Hello!

Combining directives

You can stack asConsole! or asPlayer! with delay! on the same line. The parser strips directives from the command string before executing. The order within the line does not matter — all three are detected independently.

# Run as console after 3 seconds
"asConsole! delay! 3 broadcast &a[playerName] has been here for 3 seconds"

# Run as the player immediately
"asPlayer! sethome default"

# No directive = same as asConsole!
"tell [playerName] &aWelcome to the server!"
Warning: When using asPlayer! with a delay, the player must still be online when the delay expires. If they disconnected, the command is silently skipped.

General structure of events.yml

# plugins/OreoEssentials/chat-messaging/events.yml

events:

  firstJoinServer:
    - "asConsole! tell [playerName] &aWelcome to the server!"
    - "asConsole! give [playerName] bread 8"
    - "asConsole! delay! 2 title [playerName] title {\"text\":\"Welcome!\",\"color\":\"green\"}"

  joinServer:
    - "asConsole! broadcast &a[playerName] &7joined the server."

  playerKillPlayer:
    - "asConsole! broadcast &6[playerName] &7defeated &c[victim]"
      # Give money with Vault/CMI/EssentialsX:
      # - "asConsole! eco give [playerName] 25"

  advancementDone:       # empty list = do nothing
    []

All variables

Variables are tokens in your command strings that OreoEssentials replaces with real values at the moment the event fires. They are case-sensitive and must be written exactly as shown.

VariableValueAvailable on
[playerName]The name of the player who triggered the event (actor).All events
[victim]The name of the player who was killed.playerKillPlayer
[opponent]The name of the other player in a PvP engagement.pvpstart, pvpstop
[fromWorld]The name of the world the player is leaving.playerTeleport
[toWorld]The name of the world the player is entering.playerTeleport, playerPreWorldChange, playerWorldChange
[newGameMode]The new gamemode name in ALL_CAPS (e.g. SURVIVAL, CREATIVE).playerGameModeChange
[reason]The kick reason text.playerKick
[level]The new XP level number the player just reached.playerLevelChange
[advancement]The full advancement key in namespace:path format (e.g. minecraft:story/mine_stone).advancementDone
No variable? If you reference a variable that is not available for a given event (e.g. [victim] on a joinServer event), it will remain in the command string as-is — make sure you only use variables listed as available for that event.

Event types — Join & Quit

firstJoinServer
Fires the very first time a player ever joins the server. Uses Bukkit's hasPlayedBefore() check. Fires before joinServer on the same join. Each UUID is only processed once per server session even if the check is called twice.
[playerName]
joinServer
Fires on every join, including first join. If you want something to happen on ALL joins, put it here. If you only want it on the very first join, use firstJoinServer instead.
[playerName]
quitServer
Fires when a player disconnects from the server for any reason (client disconnect, kick, server shutdown). asPlayer! commands will not fire reliably here since the player is leaving.
[playerName]
playerKick
Fires when a player is kicked by an admin or a plugin. The kick reason is provided as [reason]. Fires at MONITOR priority so the kick is already confirmed.
[playerName][reason]
playerBan
Fires on AsyncPlayerPreLoginEvent when the result is KICK_BANNED. This means it fires even for offline join attempts (the player doesn't need to be fully online). Only asConsole! commands work here — the player object may not exist.
[playerName]

Event types — Combat & PvP

playerKillPlayer
Fires when a player kills another player. [playerName] is the killer, [victim] is the player who died. Also triggers the death message system to build a player-vs-player message.
[playerName][victim]
playerRespawn
Fires after a player has respawned following death. The player is already at their respawn location when commands run. Great for respawn-protection timers or welcome-back messages.
[playerName]
pvpstart
Fires when two players engage in PvP for the first time (or after the 15-second cooldown since their last hit). Both players receive the event — [playerName] is each player, [opponent] is the other one.
[playerName][opponent]
pvpstop
Fires approximately 15 seconds after the last hit between a specific pair of players, if no new hit occurred. Both players receive the event. The 15-second window resets on every hit. See PvP tracking for full details.
[playerName][opponent]

Event types — World & Travel

playerTeleport
Fires on ANY teleport — same-world warps, cross-world teleports, /tp commands, etc. Provides both [fromWorld] and [toWorld]. For cross-world teleports, playerPreWorldChange and playerWorldChange also fire.
[playerName][fromWorld][toWorld]
playerPreWorldChange
Fires right before a cross-world teleport completes (pre-change). The player has not yet arrived in the new world. Good for "loading" messages. Only fires when the source and destination worlds differ.
[playerName][toWorld]
playerWorldChange
Fires after a player has arrived in the new world. Runs one tick after the teleport to ensure the player is in the destination world. Only fires on cross-world teleports.
[playerName][toWorld]
playerGameModeChange
Fires when any plugin or admin changes a player's gamemode. [newGameMode] contains the destination gamemode in uppercase (SURVIVAL, CREATIVE, ADVENTURE, SPECTATOR).
[playerName][newGameMode]
voidFall
Fires when a player's Y coordinate drops below 0 (detected via PlayerMoveEvent). Useful for warnings before the void kills them. Note: fires repeatedly while falling through void, not just once.
[playerName]

Event types — Activity & Misc

bedEnter
Fires after a player successfully enters a bed (sleep). Only fires when the bed-enter is not cancelled by other plugins.
[playerName]
bedLeave
Fires when a player leaves a bed (after sleeping through the night or being woken up). Fires on PlayerBedLeaveEvent.
[playerName]
playerLevelChange
Fires whenever a player's XP level changes. [level] is the new level. Fires on both level-ups and level-downs (e.g. from dying with keepInventory false).
[playerName][level]
advancementDone
Fires when a player completes any advancement (recipes, challenges, milestones). [advancement] is the full namespaced key e.g. minecraft:story/mine_stone. The default config has this as an empty list — add commands to activate it.
[playerName][advancement]
elytraStartGlide
Fires when a player activates elytra gliding (opens wings). Detected via EntityToggleGlideEvent with isGliding() = true.
[playerName]
elytraEndGlide
Fires when a player stops gliding (lands, hits water, closes wings). Detected via EntityToggleGlideEvent with isGliding() = false.
[playerName]
swapHandItems
Fires whenever a player presses the swap-hands key (default: F) to move their offhand item to mainhand or vice versa.
[playerName]
sneakingSwapHandItems
Fires when a player swaps hands while sneaking. This fires in addition to swapHandItems — both events run when the player is sneaking and swaps. Use this for sneak-specific actions.
[playerName]

Death messages — How it works

When a player dies, OreoEssentials intercepts the PlayerDeathEvent at MONITOR priority and calls DeathMessageService.buildMessage(). This method analyses the kill to determine the exact cause, then picks a random message from the appropriate section of death-messages.yml.

The resulting message replaces the vanilla death message (via event.setDeathMessage()). If cross-server messaging is enabled, the message is also serialised into a DeathMessagePacket and broadcast to all other servers via RabbitMQ so the whole network sees it.

Disabling death messages: Set Enabled: false at the top of death-messages.yml. The system returns null and vanilla death messages are restored. You can also toggle it live without a full reload.

The prefix

Every death message is prefixed with the value of Prefix: in death-messages.yml. The default is 💀 . Set it to "" to have no prefix.

Random variation

Each section (e.g. Player.Item, Mob.creeper.General) can contain multiple lines. OreoEssentials picks one at random every time a death message is needed. Add more lines to increase variety — each line has an equal probability of being selected.

Colour codes

Use legacy &X colour codes inside message strings. They are automatically converted to §X Minecraft format. Full colour code reference: &0–&9, &a–&f for colours; &l bold, &o italic, &r reset.

PlaceholderAPI support

Any %placeholder% syntax inside death message strings is processed through PlaceholderAPI (if installed) before the message is sent. This lets you include things like %vault_eco_balance% or custom stats in a death message.

Death message priority chain

The service checks causes in a strict order. The first match wins — it stops looking once it finds a non-empty list. Understanding this order is essential when you want to customise specific kills.

1
Player.Item — killed by a player holding a named/typed item

Checked first when the killer is a player AND they have something in their main hand. Uses the Player.Item section. Variables: [sourceDisplayName] (killer), [item] (item name).

2
Player.Projectile — killed by a player's projectile

Used when the damage source is a projectile (arrow, trident, fireball…) shot by a player. Uses Player.Projectile. Variables: [sourceDisplayName], [type] (projectile type). Specific sub-keys: Player.Fireball, Player.Firework, Player.Tnt.

3
Player.General — generic player kill

Fallback when the killer is a player but no item or projectile context was found. Uses Player.General. Variable: [sourceDisplayName].

4
Mythic.<InternalId> — MythicMobs boss kill

Only checked when MythicMobs is installed. Uses the mob's internal ID as the YAML key. Supports both .Item and .General sub-keys. Variables: [mobMythicId], [mobMythicName], [item]. See MythicMobs section.

5
Mob.<entity_type> — vanilla mob kill

Uses the Bukkit entity type in lowercase (e.g. Mob.creeper, Mob.skeleton). Supports both .Item and .General sub-keys. Variable: [sourceDisplayName] (the mob's display name). Falls back to Mob.primed_tnt.General if the specific mob has no entry.

6
Custom.<cause> — environmental / non-entity death

Used when no entity killer was found. The Bukkit DamageCause is mapped to a YAML path (see table below). Falls back to "[playerDisplayName] died" if nothing matched.

Death message variables

These variables are available inside death-messages.yml strings only. They are different from the event variables above.

VariableValueNotes
[playerDisplayName]The display name of the player who died (may include rank colour prefix from other plugins).Always available.
[playerName]The raw (no colours) name of the dead player.Always available.
[killerName]The plain name of the player killer.Empty string if killer is not a player.
[sourceDisplayName]The display name of whatever killed the player — player display name, MythicMobs boss display name, or prettified mob type name.Always available; prettified from entity type if not a player/mythic.
[type]The type of projectile used (e.g. arrow, trident). Prettified from Bukkit's projectile type name.Only meaningful in projectile deaths.

[mobMythicId]The MythicMobs internal mob ID (e.g. AncientOverlord).Only set when MythicMobs is installed and the killer is a mythic mob.
[mobMythicName]The MythicMobs display name of the boss.Only set when MythicMobs is installed and the killer is a mythic mob.

MythicMobs integration

OreoEssentials detects MythicMobs automatically at runtime using reflection. You do not need to configure anything — if MythicMobs is installed, the integration activates. If it is not installed, that code path is never reached.

When a player is killed by a MythicMobs entity, the service resolves:

  • The mob's internal ID (e.g. AncientOverlord) → used as the YAML key
  • The mob's display name (e.g. Ancient Overlord) → used as [mobMythicName]

Both old (io.lumine.xikage) and new (io.lumine.mythic) MythicMobs API packages are supported via separate reflection paths.

Adding MythicMobs death messages

Use the mob's exact internal ID as the key under the Mythic: section:

Mythic:
  AncientOverlord:          # exact internal MythicMobs mob ID
    General:
      - "&2[playerDisplayName] &7was obliterated by &5[mobMythicName]"
      - "&2[playerDisplayName] &7fell before the might of &5[mobMythicId]"
    Item:                     # when the boss holds a weapon
      - "&2[playerDisplayName] &7was felled by &5[mobMythicName] &7wielding &2[item]"

  FrostGiant:
    General:
      - "&2[playerDisplayName] &7was crushed by &b[mobMythicName]"
How to find the internal ID: In MythicMobs, each mob has an ID defined in its config file (e.g. AncientOverlord.yml → ID is AncientOverlord). This is case-sensitive. It is the same ID you use in /mm mobs spawn AncientOverlord.
Priority note: Mythic messages take priority 4 in the chain — higher than vanilla mobs (5) but lower than player kills (1–3). If a MythicMobs boss is killed by a player's projectile, the Player.Projectile message wins, not the Mythic one.

Cross-server death message broadcast

When RabbitMQ cross-server messaging is enabled, every death message is packaged into a DeathMessagePacket and broadcast to all other servers on the network via the GLOBAL channel.

The packet carries:

  • The dead player's UUID and name
  • The fully-formatted death message string (already coloured)
  • The originating server name

Receiving servers unpack the packet and display the message to players there, so the entire network sees the death announcement simultaneously.

No extra config needed. Cross-server death messages use the same RabbitMQ setup as the rest of OreoEssentials. If PacketManager is initialised and the message is non-empty, the broadcast fires automatically.

Command: /oevents

CommandPermissionWhat it does
/oevents reload oreo.events Reloads both events.yml and death-messages.yml from disk. No restart needed. Tab-completion suggests reload.
/oevents (no args) oreo.events Behaves the same as /oevents reload.
Permission: Only players (or console) with oreo.events can use /oevents. By default this should be given to administrators only.

PvP tracking system

The pvpstart and pvpstop events use a lightweight internal tracking system. Understanding how it works helps you use these events effectively.

How pvpstart fires

Every time a player damages another player (direct hit or via projectile), the engine checks whether the pair is already "in combat". If not, it:

  1. Records the pair in an internal map (UUID → opponent UUID)
  2. Fires pvpstart for both players with each other's name as [opponent]
  3. Schedules a 15-second stop check

If the pair is already in combat (the map entry exists), no new pvpstart fires — they are already engaged.

How pvpstop fires

Every hit reschedules a 15-second timer. When that timer expires without any new hit between the same pair:

  1. The pair is removed from the map
  2. pvpstop fires for both players (if still online)

If either player killed the other, pvpstop does not fire — the pair is no longer tracked.

Important: PvP events fire for both players involved. Your pvpstart command list will execute twice — once with [playerName] = attacker and once with [playerName] = victim. Design your commands accordingly (e.g. using tell [playerName] is fine; using broadcast would duplicate the message).

Folia compatibility

All command dispatch in the Events module goes through OreScheduler, OreoEssentials's Folia-aware scheduler wrapper. This means:

  • asConsole! commands run on the global tick thread (required by Folia for Bukkit.dispatchCommand())
  • asPlayer! commands run on the player's region thread (required by Folia for Player.performCommand())
  • delay! commands use the appropriate thread type — OreScheduler.runLaterForEntity() for player commands, OreScheduler.runLater() for console commands

On Paper (non-Folia), this adds at most a 1-tick delay for synchronisation but is otherwise transparent. No extra configuration is needed.

Frequently asked questions

My command isn't running — what's wrong?

Check these things in order:

  1. Is the event name spelled correctly and indented properly in the YAML? (YAML is indentation-sensitive.)
  2. Did you run /oevents reload after editing the file?
  3. Is the variable you used available for that event? (e.g. [victim] only exists on playerKillPlayer)
  4. If using asPlayer!, is the player still online when the command fires?
  5. Check server console for YAML parse errors — a syntax error in one section can break the whole file.

Can I run multiple commands for the same event?

Yes. Each event type takes a YAML list. Just add more lines:

joinServer:
  - "asConsole! broadcast &a[playerName] joined!"
  - "asConsole! tell [playerName] &7Welcome back."
  - "asConsole! delay! 10 tell [playerName] &7Type /help to start."

Can I disable an event without deleting it?

Yes — set it to an empty list: eventName: []. Or comment out lines with #. An empty list means the event fires but does nothing.

My death messages are still vanilla — why?

Check that Enabled: true is set at the top of death-messages.yml. Then run /oevents reload. Also check the console for YAML parse errors in the death messages file.

How do I add a death message for a mob that isn't listed?

Add a new key under Mob: using the lowercase Bukkit EntityType name. For example, for a Bogged (new 1.21 mob):

Mob:
  bogged:
    General:
      - "&2[playerDisplayName] &7was pierced by a bogged arrow"

Can I use PlaceholderAPI in event commands?

Event commands are dispatched as raw Minecraft commands — OreoEssentials does not pre-process them through PAPI. However, you can call PAPI-aware commands (like CMI or EssentialsX commands that support PAPI internally) and they will resolve placeholders themselves. In death messages, PAPI is processed by OreoEssentials before sending.

The pvpstart fires twice for a broadcast — is that a bug?

No, it is by design. See the PvP tracking section. Both players receive the event. Use tell [playerName] (private message to each player) instead of broadcast to avoid duplicate global announcements.

Does firstJoinServer fire if a player joins, gets banned, then comes back?

firstJoinServer relies on Bukkit's player.hasPlayedBefore(). Once a player has joined once, this returns true on all future joins — even if they were banned in between. So firstJoinServer only ever fires on the very first join for each UUID.

Can I add MythicMobs boss messages without MythicMobs installed?

Yes. You can add entries under Mythic: at any time. They will simply never be reached unless MythicMobs is installed and a mythic mob kills a player. There is no error or warning if the section exists but is never used.

Are death messages shown cross-server?

Yes, if RabbitMQ cross-server messaging is configured. The DeathMessagePacket is broadcast to all servers on the GLOBAL channel so all players on all servers see the death announcement. See Cross-server broadcast.
