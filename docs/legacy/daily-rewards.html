🗓️ Daily Rewards

Give players a reason to log in every day. Define up to 30 rewards (or more), each with its own icon, commands, and message. Players build a streak by claiming rewards on consecutive days — and you control exactly what happens when they miss a day. The whole system is driven by a single YAML file and a clean inventory GUI.

What is it?

Daily Rewards is a login-reward module built into OreoEssentials. Here is what it does in plain English:

  • Players run /daily (or /dailyrewards) to open an inventory GUI.
  • The GUI shows all the configured reward days. The current day is highlighted in green.
  • Players click the highlighted day to claim their reward. Commands run automatically (give money, items, run any command you want).
  • Each day they claim, their streak counter goes up by one. Miss a day and the streak resets (or pauses, depending on your config).
  • Once all days in the streak are completed it loops back to Day 1 — or stays on the last day, your choice.
Storage Options

Player data (streak, last claim date) can be saved to a plain YAML file on disk (easy, no setup) or to a MongoDB database (required if you run multiple servers and want shared data).

File Location

plugins/
  OreoEssentials/
    dailyrewards/
      dailyrewards.yml    ← Everything: settings AND rewards are here
    daily_players.yml     ← Auto-created: stores player streak/claim data (file mode)

The dailyrewards.yml file is created automatically with defaults the first time the server starts. Edit it to customise your rewards, then run /daily toggle (or simply restart) to apply changes.

No reload command

There is no hot-reload command for the rewards config. Changes to dailyrewards.yml take effect after a server restart. The /daily toggle command only enables/disables the feature at runtime — it does not re-read the file.

Quick Start — Up and Running in 4 Steps

1

Start the server once

OreoEssentials creates plugins/OreoEssentials/dailyrewards/dailyrewards.yml with a working default config: Day 1 gives 100 eco money, and Days 2–30 are blank (ready to fill in). Players can already use /daily right away.

2

Open the config and fill in your rewards

Open dailyrewards/dailyrewards.yml in a text editor. Find the Rewards: section near the bottom. Edit Days 1–7 (or however many you want). Each day needs a RewardName, a RewardIcon (a Minecraft item name), and one or more RewardCommands. See the reward fields reference below for exact syntax.

3

Restart the server

Rewards are loaded at startup. After restarting, log in and run /daily to see your new rewards in the GUI.

4

Give players the permission

Make sure players have the oreo.daily permission node. If you use LuckPerms: lp group default permission set oreo.daily true

Storage — File vs MongoDB

The first section of dailyrewards.yml controls where player data is saved. 

Storage:
  Mongo:
    Enabled: false
      # false = use plain file storage (daily_players.yml)
      # true  = use MongoDB — needed for multi-server networks

    Uri: "mongodb://user:pass@host:port/?directConnection=true"
      # Your MongoDB connection string.
      # Only used when Enabled: true.

    Database: "oreo"
      # The database name inside MongoDB.

    Collection: "oreo_"
      # The collection (table) name inside the database.

Running a single server?

Keep Mongo.Enabled: false. File storage is simpler, requires zero extra setup, and auto-saves every 5 minutes. MongoDB is only needed when players move between servers and you want their streak to follow them.

MongoDB connection fails → automatic fallback

If MongoDB is enabled but the connection fails at startup, the plugin automatically falls back to file storage and logs a warning. It will not crash or disable itself. Check your console for [Daily] MongoDB connection failed, falling back to file storage.

Claiming Behaviour

This section is the most important part of the config. These four settings control the entire streak logic. Read each one carefully. 

Claiming:
  ResetWhenStreakCompleted: true
  AvailableOnNewDay: false
  PauseStreakWhenMissed: false
  SkipMissedDays: false

ResetWhenStreakCompleted

Controls what happens when a player reaches the last configured day (e.g. Day 30 in a 30-day streak).

ValueWhat happens
true After claiming the last day (e.g. Day 30), the streak loops back to Day 1. The cycle repeats forever. This is the most common setup.
false After claiming the last day, the player stays stuck on Day 30 forever and keeps receiving the same last-day reward every day. Good if Day 30 is an "ultimate" reward you always want to give.

AvailableOnNewDay

Controls when the next reward becomes available.

ValueWhat happens
false 24-hour cadence. A player must wait a full 24 hours from their last claim. If they claimed at 3pm Monday, their next reward is available at 3pm Tuesday. This is the most fair option.
true Calendar-day cadence. A player can claim once per calendar day, regardless of time. They could claim at 11:59pm one day and again at 12:01am the next — a 2-minute gap. Easier for players but slightly exploitable.

PauseStreakWhenMissed

Controls what happens when a player skips a day without claiming.

ValueWhat happens
false Default. Missing a day resets the streak to Day 1. Players must start all over. This is the strictest and most motivating option.
true Missing a day pauses the streak where it is. The player can continue from where they left off next time they log in. They never lose progress — they just don't advance. Use this for a more relaxed experience.
Priority note

PauseStreakWhenMissed takes priority over SkipMissedDays. If pause is true, skip is ignored.

SkipMissedDays

Only relevant when PauseStreakWhenMissed: false (streak resets on miss).

ValueWhat happens
false Default. Missing a day resets the streak to Day 1 on the next claim.
true Even if days were missed, the streak increments as if they claimed every day. Missing 3 days and then claiming will advance the streak by 1 (not reset it). This is the most generous option.

How Rewards Work

All rewards are listed under the Rewards: section at the bottom of the file. Each entry starts with Day N: where N is the day number (1, 2, 3… up to 30 or more). The plugin reads them in order and builds a list.

When a player claims their daily reward, the plugin looks at their current streak to decide which day's reward to give:

  • Streak is 0 (first ever claim) → they get Day 1's reward, streak becomes 1
  • Streak is 1 → they get Day 2's reward, streak becomes 2
  • Streak is 6 → they get Day 7's reward, streak becomes 7
  • Streak is 30 (last day, ResetWhenStreakCompleted: true) → they get Day 1 again, streak becomes 1
Missing a day

If a player misses a day and PauseStreakWhenMissed: false (default), their streak resets to 0 on the next claim. The next reward they get will be Day 1 again.

How many days should you configure?

The plugin supports any number of days. The default file has 30 days pre-created (most are blank — just fill them in). Common patterns:

  • 7-day loop — Define Days 1–7. Players loop through the week forever.
  • 30-day loop — Define Days 1–30 for a full month cycle.
  • Scaling rewards — Define only 30 days with ResetWhenStreakCompleted: false. Day 30 reward is the best one; players are incentivised to keep a streak going.

Every Reward Field Explained

Here is a fully documented reward entry. Every field is optional except RewardName and RewardIcon.

Rewards:
  Day 1:
    RewardName: "Welcome"
        # The name shown on the item in the GUI for this day.
        # Supports legacy color codes: "Day &61&f Welcome"

    RewardIcon: "EMERALD"
        # The Minecraft item type used as the icon in the GUI.
        # Must be a valid material name (all caps, underscores).
        # Examples: DIAMOND, GOLD_INGOT, NETHER_STAR, SUNFLOWER,
        #            EMERALD, IRON_INGOT, BOOK, CHEST, BEACON
        # Full list: https://hub.spigotmc.org/javadocs/spigot/org/bukkit/Material.html
        # If an invalid name is given, SUNFLOWER is used as fallback.

    RewardCommands:
      - "eco give <playerName> 100"
        # A list of console commands run when the reward is claimed.
        # <playerName> is replaced with the claiming player's name.
        # Commands run as CONSOLE (full server permissions).
        # You can have multiple commands — just add more lines.
        # To have NO command, set: RewardCommands: [""]

    RewardMessage: "You claimed your Day 1 reward!"
        # Optional. A message sent to the player in chat when they claim.
        # Leave this field out entirely if you don't want a per-day message.
        # Uses legacy &X color codes.

    Extras:
      Enchanted: false
              # true = the icon item in the GUI has a visual enchantment glow.
              # The item is NOT actually given to the player — it's only visual.

      CustomModelData: 0
              # Custom model data integer for the GUI icon item.
              # 0 = no custom model data.
              # Use this if you have a resource pack with custom item models.
              # Example: 1201 will apply setCustomModelData(1201) to the item.

      GUI Position: 0
              # Optional. Force this reward into a specific GUI slot.
              # Slot 0 = top-left. Slot 8 = top-right. Slot 9 = second row left.
              # If omitted, the plugin places rewards automatically left-to-right.

      GUI Page: 1
              # Which page of the GUI this forced position applies to.
              # Only used together with "GUI Position".

Reward Commands — What Can You Do?

Each entry in RewardCommands is a console command. The placeholder <playerName> is replaced with the claiming player's exact username. Commands run instantly when the player clicks the reward in the GUI. 

RewardCommands:

    # ── Economy / Currency ────────────────────────────────────────────
  - "eco give <playerName> 500"            # Vault economy: give $500
  - "oecurrency give <playerName> gems 10"  # OreoEssentials custom currency

    # ── Items ─────────────────────────────────────────────────────────
  - "give <playerName> DIAMOND 3"          # Give 3 diamonds
  - "give <playerName> EMERALD 1"

    # ── XP ────────────────────────────────────────────────────────────
  - "xp give <playerName> 5 levels"        # Give 5 XP levels

    # ── Permissions (LuckPerms) ───────────────────────────────────────
  - "lp user <playerName> group add vip"   # Give VIP rank for Day 30

    # ── Custom messages ───────────────────────────────────────────────
  - "minecraft:tellraw <playerName> {\"text\":\"Reward claimed!\",\"color\":\"gold\"}"

    # ── Multiple commands for one day ─────────────────────────────────
  - "eco give <playerName> 1000"
  - "give <playerName> NETHER_STAR 1"
  - "broadcast <playerName> just claimed their Day 7 reward!"
Works with any plugin

Because commands run as console, they work with any plugin installed on your server — EssentialsX (eco give), CMI (cmi money give), TokenManager, Jobs, Crates, etc. Just use the same command you'd type in console, with <playerName> in place of the player's name.

Empty commands

If a day has no commands to run, set: RewardCommands: [""]. A single empty string is safely ignored. Don't leave the list completely empty or the YAML may error.

The Special "Day Example" Entry

At the top of the Rewards: section there is an entry called Day Example. This is NOT a real day — the plugin skips any entry that doesn't start with Day followed by a number. Its purpose is purely as a reference showing all available fields.

Building 30 Days — Strategy Tips

The default file has 30 entries already created (Days 1–30), most of them blank. Here's how to think about filling them in for a good player experience.

Reward scaling strategy

  • Days 1–7: Small, daily rewards. $100–500 + basic items.
  • Day 7: Weekly milestone bonus — noticeably better. A Nether Star, a key, 5 diamonds.
  • Days 8–14: Slightly better than week 1. $200–700.
  • Day 14: Two-week milestone — bigger bonus again.
  • Days 15–21 and 22–29: Keep scaling up. Rare items, more money.
  • Day 30: Best reward of the cycle. Make it worth the full month's effort.

Filling in a blank day quickly (compact YAML format)

Blank entries in the default file look like this:

  Day 8:  { RewardName: "", RewardIcon: "", RewardCommands: [""], Extras: { Enchanted: false, CustomModelData: 0 } }

Replace it with the full format and fill in your values:

  Day 8:
    RewardName: "&eDay 8"
    RewardIcon: "EMERALD"
    RewardCommands:
      - "eco give <playerName> 300"
    Extras:
      Enchanted: false
      CustomModelData: 0
Blank days still appear in the GUI

If a day has empty RewardName and RewardIcon, it appears in the GUI as "Day N" with a Sunflower icon (the fallback). If you want to skip gaps, remove those entries entirely from the config. Only configure the days you actually want.

A streak is just a counter that goes up by 1 each time you claim a reward on consecutive days.

What happens after the miss depends on your config:

  • Default (PauseStreakWhenMissed: false, SkipMissedDays: false): Streak resets to 0 → they get Day 1 reward again.
  • PauseStreakWhenMissed: true: Streak stays at 3 → they continue with Day 4 reward.
  • SkipMissedDays: true: Streak increments to 4 → they get Day 4 reward (as if they never missed).

Streak Scenarios — Real Examples

Scenario 1: Player plays every day for 7 days (all modes)

They get Day 1, Day 2, Day 3 … Day 7. Streak reaches 7. With ResetWhenStreakCompleted: true, the next claim resets to Day 1 again. With false, Day 7 reward is given forever.

Scenario 2: Player misses Day 4 (default config)

Claimed Days 1, 2, 3. Streak = 3. Skipped Day 4. On Day 5, they log in and claim. The gap between last claim and today is 2 days (not 1), so the streak resets to 1. They receive the Day 1 reward again.

Scenario 3: Player misses Day 4 (PauseStreakWhenMissed: true)

Claimed Days 1, 2, 3. Streak = 3. Skipped Day 4. On Day 5, they log in and claim. Gap is 2 days, but since pause is true, the streak stays at 3. They receive Day 4's reward. Streak becomes 4.

Scenario 4: Player completes all 30 days (ResetWhenStreakCompleted: true)

After claiming Day 30, their streak resets to 0. The next day they claim again, they get Day 1. The cycle repeats indefinitely.

Scenario 5: Player completes all 30 days (ResetWhenStreakCompleted: false)

After claiming Day 30, their streak is at 30. On Day 31, nextDayIndex caps at 30 (max day). They keep receiving Day 30's reward forever — the "best" reward on every claim going forward.

In-Game GUI Overview

When a player runs /daily, an inventory GUI opens. Here's what they see:

  • Main area — one slot per configured reward day. Items show the day's icon and name.
  • Bottom row (last row) — navigation bar with three buttons:
    • Left arrow (slot 0) — Previous page
    • Player head (slot 4) — Shows the player's name, current streak, and today's day index
    • Right arrow (slot 8) — Next page
    • Lever (slot 5) — Admin only: toggle Daily Rewards on/off without commands

If there are more days than fit on one page (InventoryRows - 1 rows × 9 columns), the GUI automatically paginates. Players use the arrows to navigate pages.

Admin Controls in the GUI

Players with the oreo.daily.admin permission see an extra button in the navigation bar: a Lever in slot 5 of the bottom row.

  • The lever shows the current state: ENABLED or DISABLED
  • Clicking it toggles the feature on/off instantly — same as running /daily toggle
  • The GUI refreshes immediately after clicking to reflect the new state
  • The new state is saved to the config file automatically

Data File — daily_players.yml

When using file storage (MongoDB disabled), all player streak data is stored in plugins/OreoEssentials/daily_players.yml. This file is auto-created and auto-saved every 5 minutes. You should never need to edit it manually, but knowing its structure is useful for troubleshooting. 

players:
  069a79f4-44e9-4726-a5be-fca90e38aaf5:   # Player's UUID
    name: "Notch"                           # Last known username
    streak: 7                              # Current streak count
    lastClaimEpochDay: 19850              # Days since 1970-01-01 (internal date)
    totalClaims: 42                       # Total number of times ever claimed

  853c80ef-3c37-49fd-aa49-938b674adae6:
    name: "Steve"
    streak: 1
    lastClaimEpochDay: 19849
    totalClaims: 3

Manually resetting a player's streak

To reset a player's streak (e.g. for a punishment or a bug fix), stop the server, find their UUID entry in daily_players.yml, and set streak: 0 and lastClaimEpochDay: 0. Save the file and restart.

Never edit while server is running

The file is read into memory at startup and saved periodically. If you edit it while the server is running, your changes will be overwritten on the next auto-save. Always stop the server first.

FAQ / Troubleshooting

Q: Players can't use /daily — "no permission" error.

They need the oreo.daily permission. Run: lp group default permission set oreo.daily true

Q: I edited the rewards but they didn't change in-game.

Rewards are loaded at server startup. There is no hot-reload for dailyrewards.yml. You must restart the server after editing it. The /daily toggle command only turns the feature on/off — it does not re-read the config file.

Q: The reward icon shows a Sunflower instead of what I configured.

The RewardIcon value is invalid or misspelled. Material names must be UPPERCASE with underscores (e.g., GOLD_INGOT, NETHER_STAR). The plugin falls back to SUNFLOWER when it can't find the material. Check the exact spelling at the Bukkit Material javadoc.

Q: The reward commands aren't running.

Check these things in order:

  1. Is the command syntax correct? Test it in console manually by typing it with a real player name.
  2. Is <playerName> spelled exactly right (with the angle brackets)?
  3. Is the plugin the command belongs to actually installed and enabled?
  4. Check the server console for error messages at the moment of claiming.

Q: The streak isn't resetting when players miss a day.

Check your Claiming: settings. If PauseStreakWhenMissed: true, missing a day intentionally keeps the streak. If you want resets on miss, both PauseStreakWhenMissed and SkipMissedDays must be false.

Q: Player says they can claim multiple times per day.

This happens if AvailableOnNewDay: true is set. This mode allows claiming once per calendar day, so a player can claim at 11:59pm and again at 12:01am. Set it to false to enforce a strict 24-hour wait between claims.

Q: I want to give 30 days of unique rewards but also keep looping indefinitely.

Set ResetWhenStreakCompleted: true and configure 30 days. After Day 30, the streak resets to 1 and the player starts from Day 1 again. They'll go through the full 30-day cycle every month.

Q: I want the last day to be a "permanent VIP" reward that players only get once ever.

Use a command like lp user <playerName> group add vip on Day 30. LuckPerms won't error if the player is already in the group — it's idempotent. Even if the streak resets and they reach Day 30 again, running the command again is harmless. If you truly want it only once, use ResetWhenStreakCompleted: false so they stay on Day 30 and keep getting the same reward — but then set the Day 30 reward to something smaller, since it's given every day forever.

Q: MongoDB says "connection failed" — what to check?

  1. Is the MongoDB server actually running?
  2. Is the URI in Storage.Mongo.Uri correct? Test it with MongoDB Compass or mongosh.
  3. Does the user in the URI have read/write permission on the specified database?
  4. Is the port open / not blocked by a firewall?
  5. The plugin will automatically fall back to file storage if the connection fails — data won't be lost, it just won't be shared across servers.

Q: How do I check a player's current streak without opening the GUI?

Run /daily top — it shows the top 10 streaks including all online players. For a specific player, you can look in daily_players.yml (file mode) or query MongoDB directly.

Q: Can I add more than 30 days?

Yes. Just add more entries: Day 31:, Day 32:, etc. The plugin supports any number of days. More entries = more pages in the GUI (automatically paginated).
