🎁 What is Playtime Rewards?

Playtime Rewards is a built-in module in OreoEssentials that automatically gives players rewards based on how long they have played on your server. Think of it as a loyalty programme — the more hours a player puts in, the more they earn.

There are two reward flavours:

⭐ One-Time Milestones

Trigger once when a player's total playtime reaches a threshold — for example a big cash bonus at 24 hours. Once claimed, it never fires again for that player.

🔄 Repeating Rewards

Fire every N seconds of playtime — for example a small payment every hour. They keep coming back as long as the player keeps playing.

Both types support AutoClaim (reward fires silently in the background) or Manual Claim (reward shows in a GUI and the player must click it to collect).

The plugin tracks each player's playtime internally and saves it to disk so progress is never lost across restarts.

🚀 Quick-Start (5 steps)

New to this module? Follow these 5 steps and you'll have working rewards in under 5 minutes.
  1. Install OreoEssentials Drop OreoEssentials.jar into your plugins/ folder and start the server once. The module creates plugins/OreoEssentials/playtime-rewards/playtime_rewards.yml automatically.
  2. Open the config Edit playtime-rewards/playtime_rewards.yml. You'll see example rewards already there — you can use those or replace them with your own (see the Config File section).
  3. Give players access By default all "public" rewards (those without requires-permission: true) are visible to every player — no permission needed. If you want rank-only VIP rewards, add requires-permission: true and assign oreo.prewards.<reward-id> via LuckPerms.
    Give players the oreo.prewards.notify permission so they get a reminder message when a reward is ready to collect.
  4. Reload or restart Either restart your server or run /prewards reload (requires oreo.prewards.admin).
  5. Test it As a player (or use /prewards claim <id> <player> as admin) run /prewards to open the GUI. Rewards that are ready show in green/glowing and can be clicked to claim.

⚙️ Config File Explained

Everything lives in one file: plugins/OreoEssentials/playtime-rewards/playtime_rewards.yml. Here is a fully annotated version of the settings section: 

settings:

  # ── How playtime is measured ──────────────────────────────────────
  source: internal
  # "internal" = OreoEssentials tracks time itself (recommended)
  # "bukkit"   = uses Minecraft's vanilla statistic (counts ALL servers)

  baseline-from-bukkit-on-first-seen: true
  # true  = first time a player is seen, copy their existing Bukkit
  #         playtime into the internal tracker so long-time players
  #         don't suddenly "lose" progress when you switch to internal.
  # false = start counting from zero when first seen.

  baseline-on-first-seen: true
  # true  = when first seen, mark all repeating rewards as already
  #         paid-up to current playtime (prevents a burst of back-pay).
  # false = player gets all missed repeating rewards on first login.

  notify-every-minutes: 10
  # How often (in real-time minutes) online players are reminded
  # if they have unclaimed manual rewards. 0 = notifications off.

  stack-rewards: true
  # Global default for repeating rewards.
  # true  = if a player missed 3 cycles while offline, they get 3 payouts.
  # false = at most 1 payout per claim, no catch-up.

  # ── GUI appearance ────────────────────────────────────────────────
  gui:
    title: "&bPlaytime Rewards"     # inventory title (&b = aqua)
    rows: 5                        # 1 to 6 rows tall
    fill-empty: true             # fill unused slots with the filler item

    filler:                        # the background glass pane
      material: GRAY_STAINED_GLASS_PANE
      name: "&7"                   # blank name (just a space)
      custom-model-data: 0        # 0 = none

    states:                        # how each reward state looks in the GUI
      LOCKED:
        material: BARRIER         # red X — not earned yet
        name:     "&cLocked"
        glow:     false
      READY:
        material: LIME_DYE         # glowing green — click to collect!
        name:     "&aClick to claim"
        glow:     true
      CLAIMED:
        material: SUNFLOWER        # one-time rewards, already collected
        name:     "&eClaimed"
        glow:     false
      REPEATING:
        material: CLOCK            # repeating reward, ticking but not ready
        name:     "&6Repeating"
        glow:     true

📋 Reward Types

⭐ One-Time Milestones (PayFor)

Use PayFor to define a playtime threshold in seconds. When the player's total playtime reaches that number, the reward becomes claimable. It can only be claimed once per player, ever. Once collected it shows as CLAIMED in the GUI. 

# Example: one-time reward at exactly 1 hour (3600 seconds)
"1hour":
  DisplayName: "&fOne Hour Milestone"
  AutoClaim: false
  PayFor: 3600          # 3600 sec = 1 hour
  Commands:
    - "asConsole! money give [playerName] 500"
  gui:
    slot: 14
    icon:
      material: IRON_INGOT
      name: "&f1h Milestone"
Seconds reference 1 hour = 3 600  |  6 hours = 21 600  |  12 hours = 43 200  |  24 hours = 86 400  |  7 days = 604 800  |  30 days = 2 592 000

🔄 Repeating Rewards (PayEvery)

Use PayEvery instead of PayFor to define a cycle length in seconds. Every time the player accumulates another full cycle of playtime, the reward fires again — indefinitely.

For example, PayEvery: 3600 pays every hour. After 5 hours of total playtime the player will have been paid 5 times. 

# Example: pay every hour of playtime, auto-claimed
hourly1:
  DisplayName: "&7Hourly Reward"
  AutoClaim: true
  PayEvery: 3600        # trigger once per hour of playtime
  StackRewards: true    # catch up missed hours when player logs back in
  Commands:
    - "asConsole! money give [playerName] 20"
  gui:
    slot: 10
    icon:
      material: GOLD_NUGGET
      name: "&eHourly Reward"
Don't use both PayFor and PayEvery on the same reward. Use one or the other. If both are set, PayFor wins (the reward behaves as one-time).

🤖 AutoClaim vs Manual Claim

AutoClaim: true

The plugin claims the reward automatically in the background the next time the periodic check runs (every 30 seconds) or when the player joins. The player just gets the reward — no clicking needed. Great for passive income.

AutoClaim: false

The reward waits in the GUI as READY. The player must open /prewards and click the item to collect it. The item glows to draw attention. Good for milestone moments you want players to experience.

📜 Command Directives

Each command line in a reward's Commands: list can start with a directive that controls how and when it runs. Without a directive, commands default to running as the console immediately.

DirectiveFormatWhat it does
asConsole! asConsole! <command> Run the command as the server console (OP-level). This is the default if you write no directive.
asPlayer! asPlayer! <command> Run the command as the player themselves. The player needs permission for whatever command you run.
delay! delay! <seconds> <command> Wait the given number of seconds, then run the command. Pair with asConsole! or asPlayer! by writing them after the delay portion.

Placeholder

PlaceholderReplaced with
[playerName]The exact in-game name of the player who earned the reward

Examples

Commands:
  # Give money via console (most common)
  - "asConsole! money give [playerName] 500"

  # Give a kit as the player (player must have kit permission)
  - "asPlayer! kit starter"

  # Add a 5-second delay then heal them
  - "delay! 5 asConsole! heal [playerName]"

  # Broadcast an announcement immediately
  - "asConsole! broadcast &6[playerName] &ejust earned a milestone reward!"

  # Give a custom item after 2 seconds
  - "delay! 2 asConsole! give [playerName] diamond 3"
Directive order matters. Always put delay! first if combining with asConsole! or asPlayer!. Example: "delay! 3 asConsole! say hi". Writing asConsole! before delay! will not work as expected.

🖼️ GUI & Skins

When a player runs /prewards, they see a SmartInventory GUI showing all rewards they have access to. Here's what each part means:

Slot layout (rows × 9 columns)

Slots are numbered 0-based, left-to-right, top-to-bottom. Row 0 = first row, Row 1 = second row, etc. Each row has 9 columns (0–8). So: 

Slot = (row × 9) + column

Row 0:  slots  0  1  2  3  4  5  6  7  8
Row 1:  slots  9 10 11 12 13 14 15 16 17
Row 2:  slots 18 19 20 21 22 23 24 25 26
Row 3:  slots 27 28 29 30 31 32 33 34 35
Row 4:  slots 36 37 38 39 40 41 42 43 44  ← last row of a 5-row GUI
If you do NOT set a gui.slot for a reward, it auto-fills left-to-right starting from slot 10 (row 1, col 1). This means if you mix explicit slots and auto-flow rewards, make sure they don't overlap. Best practice: either give every reward an explicit slot, or give none of them one.

Per-reward icon configuration

gui:
  slot: 14                  # row 1, col 5 (optional)
  icon:
    material: IRON_INGOT     # Bukkit material name
    custom-model-data: 0  # 0 = none; set for custom resource pack items
    name: "&f1h Milestone"   # display name in GUI (supports &X colors)
    lore:
      - "&7One-time reward at &f1h&7 total."
      - "&7Status shows &aREADY &7when claimable."

The icon is then overlaid by the global state skin. For example, when a reward is LOCKED the item is replaced by a BARRIER and the name changes to &cLocked. When it becomes READY it switches to LIME_DYE with a glow enchant.

You can override the state skins globally under settings.gui.states to match your server's resource pack.

Admin toggle in GUI

If you have the oreo.prewards.admin permission, a Lever item appears in the bottom-center slot. Clicking it toggles the entire Playtime Rewards module on or off live, without restarting the server.

🚦 Reward States

Every reward is always in one of four states. The GUI uses different icons/colors for each so players instantly understand their progress.

🔒 LOCKED
✅ READY
⭐ CLAIMED
🔁 REPEATING
StateWhen it appliesWhat the player sees
LOCKED Playtime hasn't reached the threshold yet (one-time), or the next cycle isn't complete (repeating) A red BARRIER item. Cannot be clicked.
READY Threshold reached and not yet claimed (one-time), or at least one new cycle completed (repeating) A glowing LIME_DYE (or the reward's own icon with glow). Click to collect.
CLAIMED One-time reward already collected A SUNFLOWER. Can never be collected again.
REPEATING Repeating reward that is up-to-date — no new cycle due yet A CLOCK (ticking). Normal state between pay-outs.
AutoClaim rewards skip the GUI entirely. When AutoClaim: true, the plugin claims the reward automatically the moment it becomes READY — the player never has to click anything. They will still see the reward in the GUI, but it transitions straight from LOCKED → (auto-claimed) → REPEATING or CLAIMED.

📦 Stacking Offline Rewards

What happens when a player earns 3 hourly rewards while offline? The answer depends on StackRewards.

StackRewards: true

All missed cycles are paid out at once when the player logs back in. If they missed 3 hours, they get 3× the reward automatically (for AutoClaim) or see "3 ready" in the GUI (for manual).

Good for economy servers where every hour genuinely earns money.

StackRewards: false

No matter how many cycles were missed, at most 1 payout is given per claim. Prevents large cash injections from AFK farming or coming back after a long break.

Good for rare/valuable items.

You can set StackRewards globally in settings.stack-rewards and then override it per reward with the StackRewards key on that individual reward entry. 

# Global default (applies to all rewards unless overridden)
settings:
  stack-rewards: true

rewards:
  hourly1:
    StackRewards: true   # ← per-reward override
    # ...
  rare_kit:
    StackRewards: false  # only 1 at a time for rare kits
    # ...

⏱️ Playtime Source

There are two ways the plugin can measure how long a player has played:

SourceWhere it reads fromPros / Cons
internal Recommended OreoEssentials tracks login/logout times itself in playtime_data.yml ✅ Per-server tracking
✅ Survives AFK plugins (plugin sees raw connection time)
✅ Saved on quit + autosave every 60s
⚠️ Starts at 0 for new players unless baseline is enabled
bukkit Minecraft's built-in PLAY_ONE_MINUTE statistic ✅ No extra data file
⚠️ Counts ALL servers (BungeeCord)
⚠️ Ticks / 20 = seconds (rounding)
⚠️ Can be reset by vanilla stat wipes

Baseline: preventing back-pay on switch

If you switch from bukkit to internal (or install the plugin on an existing server), long-time players would suddenly appear to have 0 playtime in the internal tracker — meaning they'd hit every milestone reward the moment they log in.

To prevent this, set both baseline options to true: 

settings:
  source: internal
  baseline-from-bukkit-on-first-seen: true   # ← copies existing vanilla time
  baseline-on-first-seen: true               # ← marks repeating rewards as caught-up

With this config, the first time each player logs in after installing the plugin:

  1. Their existing vanilla playtime is copied into the internal tracker.
  2. All repeating rewards are marked as "paid up to now" so no burst payout happens.
  3. One-time milestone rewards they already "earned" by time will be immediately claimable — that's intentional.

🔑 Permission-Gated Rewards

You can make certain rewards only available to specific ranks (VIP, MVP, etc.) using the requires-permission flag.

How it works

Config settingWho sees the reward?
requires-permission: false (or omitted) Everyone — no permission needed. This is the default for all standard rewards.
requires-permission: true Only players who have oreo.prewards.<reward-id> or oreo.prewards.*
Rewards with requires-permission: false are truly public. You do NOT need to give players any special permission to see them. The GUI shows them automatically to every player on the server.

Setting up VIP/MVP rewards with LuckPerms

First, define the rank reward in the config with requires-permission: true: 

rewards:
  vip_hourly:
    DisplayName: "&6VIP Hourly"
    AutoClaim: true
    requires-permission: true    # ← only VIPs see this
    PayEvery: 3600
    Commands:
      - "asConsole! money give [playerName] 75"

Then give the permission to the VIP group via LuckPerms:

# In the Minecraft console or LuckPerms editor:
/lp group vip permission set oreo.prewards.vip_hourly true
/lp group mvp permission set oreo.prewards.mvp_daily true

Members of the VIP group will now see vip_hourly in their GUI while regular players will not.

🛡️ Permissions Table

PermissionDefaultWhat it grants
oreo.prewards.notify true Receive the reminder chat message every N minutes when rewards are ready
oreo.prewards.admin op Use /prewards reload, /prewards toggle, /prewards claim <id> <player>, and the toggle lever in the GUI
oreo.prewards.claim.others op Use /prewards claim <id> <player> to force-claim a reward for another player
oreo.prewards.<reward-id> none Access a specific reward when that reward has requires-permission: true
oreo.prewards.* op Access ALL permission-gated rewards (wildcard)

💬 Commands

CommandPermissionDescription
/prewards none Open the Playtime Rewards GUI (players only). Shows all rewards you have access to and their current state.
/prewards claim <id> none (self-claim) Claim a specific reward by its config ID (e.g. /prewards claim 1hour). Only works if the reward is in READY state for you.
/prewards claim <id> <player> oreo.prewards.claim.others Force-claim a reward for another online player. Useful for compensation or testing.
/prewards reload oreo.prewards.admin Reload playtime_rewards.yml from disk and restart the reward checker. Online players' reminder timers restart too.
/prewards toggle oreo.prewards.admin Enable or disable the entire Playtime Rewards module live. The state is saved to the config file so it persists across restarts.
Reward IDs are the config keys. In the example config, the IDs are: hourly1, daily1, 1hour, 6hour, 12hour, 24hour, 7days, 30days, vip_hourly, mvp_daily. Use these exact strings with /prewards claim.

💾 Data Files

The plugin creates these files inside plugins/OreoEssentials/:

FileContentsWhen saved
playtime-rewards/playtime_rewards.yml All configuration: settings, GUI skin, reward definitions Generated on first boot; updated only when toggling enable/disable
playtime_data.yml Per-player total playtime in seconds (internal tracker) Every 60 seconds (autosave) + on each player quit
prewards_data.yml Per-player claimed rewards (one-time IDs) + repeating pay counts Async after every claim event

playtime_data.yml structure

# plugins/OreoEssentials/playtime_data.yml
totals:
  069a79f4-44e9-4726-a5be-fca90e38aaf5: 9000   # Notch: 9000 sec (2.5 hours)
  8667ba71-b85a-4004-af54-457a9734efa7: 25200  # Alex: 7 hours

baselined:
  - "069a79f4-44e9-4726-a5be-fca90e38aaf5"  # players who have been baseline-copied
  - "8667ba71-b85a-4004-af54-457a9734efa7"
The tracker is live — it accounts for the current session. Even if a player has 3 600 seconds saved in the file, if they have been online for another 300 seconds in this session, getSeconds() returns 3 900. The session delta is added on-the-fly without writing to disk.

prewards_data.yml structure

# plugins/OreoEssentials/prewards_data.yml
069a79f4-44e9-4726-a5be-fca90e38aaf5:    # Notch's UUID
  claimedOnce:
    - 1hour          # one-time rewards he has claimed
    - 6hour
  paidCounts:
    hourly1: 7       # repeating: paid 7 times so far
    daily1: 0        # repeating: 0 full days yet
    __baseline__: 1  # internal sentinel: baseline was applied
Don't manually edit prewards_data.yml while the server is running. The file is loaded into memory on startup. Changes made to the file while the server is running will be overwritten the next time a player claims something. Stop the server, edit, then restart.

❓ FAQ

Q: Players open /prewards and see an empty GUI with no rewards. Why?

This usually means all rewards in your config have requires-permission: true. Rewards with this flag are hidden from players who don't have the oreo.prewards.<id> permission. For rewards you want everyone to see, make sure requires-permission is either false or simply not present (it defaults to false).

Q: A player just joined for the first time and instantly got a flood of reward payouts. How do I stop that?

Enable the baseline settings: 

settings:
  baseline-from-bukkit-on-first-seen: true
  baseline-on-first-seen: true

With both enabled, the plugin copies the player's existing playtime from Bukkit on first login, and marks all repeating rewards as paid-up to that point. No back-pay burst occurs.

Q: I changed a reward's PayEvery value in the config. Do existing players get back-pay?

No — the plugin compares paid count vs should-have-been-paid count at the moment of the next check. Changing a cycle length can make should = secs / newPayEvery suddenly larger than the saved count, which would trigger a catch-up. If that's a concern, run /prewards reload when no players are online, or set StackRewards: false on that reward to cap catch-up at 1.

Q: Can I have a reward that runs multiple commands?

Yes. The Commands: list accepts as many lines as you want. They all run in sequence when the reward triggers. 

Commands:
  - "asConsole! money give [playerName] 500"
  - "asConsole! give [playerName] diamond 3"
  - "asConsole! broadcast &6[playerName] claimed the 1h milestone!"
  - "delay! 2 asPlayer! kit starter"
Q: Can I disable the whole module without removing it?

Yes, two ways:
1. Run /prewards toggle — takes effect immediately and saves to config.
2. Add settings.enable: false to playtime_rewards.yml and run /prewards reload.
When disabled, players see a "Playtime Rewards are disabled" message and the GUI grays out.

Q: Will playtime data survive a server restart?

Yes. The internal tracker saves to playtime_data.yml on every player quit AND every 60 seconds while the server is running. Even if the server crashes, players lose at most ~60 seconds of tracked playtime. Claim records (prewards_data.yml) are saved asynchronously after every claim.

Q: How do I grant bonus claim checks? Can I force-claim a reward for a player?

Use /prewards claim <reward-id> <player-name>. This requires oreo.prewards.claim.others. It triggers the reward for the target player as if they'd clicked it in the GUI — commands run, data is saved, state updates.

Q: Can I use PAPI / PlaceholderAPI in commands?

Directly in the reward Commands: list, only [playerName] is replaced. If the command you're running (e.g. a custom plugin command) already processes PAPI placeholders itself, those will work. But the reward runner itself does not call PAPI.

Q: I removed a reward from the config. What happens to players who had it claimed?

The claim record stays in prewards_data.yml under that reward's ID, but since the reward no longer exists in config it is simply ignored. No error occurs. If you add the reward back later with the same ID, those players will still show it as CLAIMED.

Q: Is this compatible with Folia?

Yes. The module uses OreScheduler for all tasks, which is OreoEssentials' Folia-compatible scheduler wrapper. No direct BukkitScheduler calls are made.

Q: Can a reward be both one-time AND repeating at the same time?

No. Use either PayFor (one-time) or PayEvery (repeating). If both are set, PayFor takes precedence and the reward behaves as a one-time milestone.
