🌀 What are Portals?

A portal is an invisible 3D region in your world. When a player walks into the region, they are immediately teleported to a destination you configured. Portals look like nothing from the outside — they're defined by two corner positions (POS1 and POS2) forming a bounding box. Any block in between is part of the portal.

You can use portals for:

🏠 Hub shortcuts

Teleport players from spawn to a minigame lobby or resource world by walking through a doorway.

🌍 World gates

Connect different worlds — walk through an arch and arrive at an adventure map, skyblock island, etc.

🔗 Cross-server links

Send players to a completely different server in your BungeeCord/Velocity network automatically.

🔒 VIP areas

Block non-VIP players from entering a portal region using a permission node — they get a message instead of teleporting.

🚀 Quick-Start (5 steps)

Just want a basic portal in 2 minutes? Follow these steps and you'll have a working teleport zone before you know it.
  1. Install OreoEssentials Drop the jar into plugins/ and start the server once. The plugin creates plugins/OreoEssentials/portals/config.yml and portals/portals.yml automatically.
  2. Get the wand Run /portal wand in-game. You receive a Blaze Rod with a special name — this is your selection tool. (You need oreo.portals.create permission, or be OP.)
  3. Select the portal region Stand at one corner of the area you want to be the portal and left-click a block — this sets POS1. Go to the opposite corner and right-click a block — this sets POS2. The region between POS1 and POS2 will become the portal.
  4. Create the portal Stand at the location where you want the portal to teleport players to and run: 
    /portal create myportal <destWorld> <x> <y> <z>
    Replace <destWorld>, <x>, <y>, <z> with the actual destination coordinates. Example: /portal create lobby world 0 64 0
  5. Walk through it! Step into the region you just defined and you should be teleported immediately. If something goes wrong, check the FAQ section at the bottom.

⚙️ config.yml Explained

Location: plugins/OreoEssentials/portals/config.yml

# ── Which server this is (for cross-server portals) ───────────────
server-name: ""
# Set this to the server's name as registered in your proxy.
# Example: server-name: "survival"
# Leave empty on single-server setups.

# ── Cooldown ──────────────────────────────────────────────────────
cooldown-ms: 1000
# Milliseconds before the same player can use ANY portal again.
# 1000ms = 1 second. Prevents players from rapidly re-entering.

# ── Volume limit ──────────────────────────────────────────────────
max-portal-volume: 100000
# Maximum blocks a portal bounding box can span.
# Prevents admins from accidentally defining 1-million-block zones.

# ── Yaw/Pitch ─────────────────────────────────────────────────────
allow-keep-yaw-pitch: true
# Master switch for the per-portal "keepYawPitch" feature.
# When false, yaw/pitch is NEVER preserved regardless of portal settings.

# ── Teleportation ─────────────────────────────────────────────────
teleport-async: false
# true  = use Paper's async teleportation (required for Folia).
# false = use standard synchronous teleportation (fine for Paper).
# The plugin auto-detects Folia and forces async mode when running on it.

# ── Default teleport effects ──────────────────────────────────────
default-sound: "ENTITY_ENDERMAN_TELEPORT"
# Sound played when ANY portal teleports a player (global default).
# Use Bukkit sound names (ENTITY_ENDERMAN_TELEPORT, BLOCK_PORTAL_TRIGGER, etc.)
# or namespaced keys (minecraft:entity.enderman.teleport).

default-particles:
  type:  "PORTAL"     # Particle name (e.g. PORTAL, FLAME, END_ROD)
  count: 20          # How many particles to spawn on teleport

# ── Ambient particles ─────────────────────────────────────────────
ambient-particles:
  enabled:        false
  # true = all portals with ambient enabled get continuous particles.
  type:           "PORTAL"
  count:          3
  interval-ticks: 10
  # Spawn ambient particles every N ticks (20 ticks = 1 second).

# ── Selection wand ────────────────────────────────────────────────
wand:

🔨 Creating a Portal

Every portal needs two things: a region (the area players walk through) and a destination (where they arrive). There are two ways to define the region.

Method 1: The Wand (Recommended for Beginners)

The wand is the easiest way. Here's a step-by-step:

  1. Get the wand Type /portal wand. A Blaze Rod appears in your inventory. Hold it in your hand.
  2. Set POS1 (first corner) Walk to the first corner of your portal area. This should be the bottom corner of the region. While holding the wand, left-click any block in that area. You'll see a message: "POS1 set → world (x, y, z)".
  3. Set POS2 (opposite corner) Walk to the diagonally opposite corner — the top corner of the region. Right-click any block there. You'll see: "POS2 set → world (x, y, z)".
  4. Create the portal Now decide where you want players to end up. Run: 
    /portal create <name> <world> <x> <y> <z>
    Example: you want a portal named "spawn" that sends players to world "world" at coordinates 100, 65, 200: 
    /portal create spawn world 100 65 200
How big should the region be? The region only needs to be as big as the area players will walk through. For a doorway portal, select 2 blocks wide × 3 blocks tall (just the door opening). The portal is invisible — players won't see anything unless you add ambient particles.

Method 2: Command-Only (pos1 / pos2 subcommands)

If you prefer not to use the wand item, you can set positions by standing at each corner and running commands: 

# Stand at your first corner, then:
/portal pos1

# Walk to the opposite corner, then:
/portal pos2

# Create the portal (both methods use the same create command):
/portal create mygate world 50 64 50

Full create syntax

/portal create <name> <destWorld> <x> <y> <z> [keepYaw] [destServer] [permission]
ArgumentRequired?Description
<name>requiredUnique name for this portal (e.g. hub_gate). Stored lowercase.
<destWorld>requiredDestination world name (must be loaded on this server)
<x> <y> <z>requiredDestination coordinates (decimal numbers)
[keepYaw]optionaltrue or false — preserve player's look direction
[destServer]optionalTarget server name for cross-server teleport (none = same server)
[permission]optionalPermission node required to use this portal (none = public)

💾 portals.yml Structure

Every portal is saved to plugins/OreoEssentials/portals/portals.yml. This file is managed automatically by the plugin but it's useful to understand its format, especially for debugging. 

# plugins/OreoEssentials/portals/portals.yml

portals:
  lobby_gate:                       # portal ID (always lowercase)
    name:        lobby_gate         # original display name
    world:       survival           # world where the portal region exists
    box:
      x1: 100.0  y1: 64.0  z1: 200.0  # one corner (min)
      x2: 102.0  y2: 67.0  z2: 200.0  # opposite corner (max)
    dest:
      world: lobby                   # destination world
      x:     0.5
      y:     65.0
      z:     0.5
      yaw:   180.0                   # facing direction (0=south, 90=west, 180=north, 270=east)
      pitch: 0.0
    keepYawPitch: false               # if true, player keeps their own look direction
    permission:   null                 # null or a permission node string
    destServer:   null                 # null = same server; "lobby" = cross-server
    destWarp:     null                 # null = use coords; "spawn" = use a /warp destination
    particles:
      teleport-type:   ""              # "" = global default
      teleport-count:  -1              # -1 = global default
      ambient-enabled: false
      ambient-type:    ""
      ambient-count:   3
Don't edit portals.yml while the server is running. The file is loaded into memory. Manual edits are ignored until you run /portal reload. Changes made by the plugin (via commands or GUI) are written immediately and will overwrite your manual edits.

🔒 Permission-Locked Portals

You can restrict a portal so only certain players can use it. When a player without the required permission walks into the region, they receive a message and are not teleported.

Setting a permission at creation time

# Positional args: name world x y z keepYaw destServer permission
/portal create vip_zone lobby 0 64 0 false none oreo.vip

Setting/changing a permission via GUI

Open /portal gui, click the portal, then click Set Permission. The GUI closes and you type the permission node in chat (or none to clear it).

Assigning the permission with LuckPerms

/lp group vip permission set oreo.vip true

All players in the vip group can now use the portal. Non-VIP players get the message: "You don't have permission to use this portal."

Denied players get the message once per 5 seconds. The plugin tracks the last portal that denied each player and won't spam the message if they keep standing in the region.

🧭 Keep Yaw/Pitch

By default, when a player teleports through a portal they face the direction stored in the portal's destination (the yaw and pitch values). This is useful for having them "arrive" facing the right way.

If you enable keepYawPitch on a portal, the player's camera direction is preserved across the teleport — they come out on the other side still looking the same way they were looking when they entered.

keepYawPitch: false (default)

Player faces the destination's configured yaw/pitch after teleport. Useful when you want them to always look at something specific on arrival (like the exit portal or a sign).

keepYawPitch: true

Player keeps their own camera direction. Good for seamless-feeling portals where the transition should feel natural.

Toggle it via GUI (Keep Yaw/Pitch button) or recreate the portal with true as the 6th argument. The global allow-keep-yaw-pitch: false in config.yml disables this feature entirely for all portals.

✨ Particles

Portals support two types of particles, each configurable globally in config.yml and per-portal via the GUI.

Teleport Particles

Spawned once at the player's location when they teleport. Controlled by default-particles globally and per-portal overrides in the Particles GUI.

Ambient Particles

Spawn continuously at random positions inside the portal region every N ticks. Disabled by default. Enable globally in ambient-particles.enabled: true and per-portal in the GUI.

Setting particles via GUI

  1. Open /portal gui Click the portal you want to edit.
  2. Click "Particles" button A 5-row GUI opens showing preset particle types and count options.
  3. Pick a type Row 1 shows teleport particle presets (PORTAL, FLAME, END_ROD, etc.). Click one to set it. Active selection glows.
  4. Pick a count Row 2 shows count options (×5, ×10, ×20, ×40, ×80). Click one.
  5. Configure ambient particles (optional) Row 3 has the ambient toggle and type presets. Enable it here if desired.
Per-portal overrides take priority over global defaults. Setting a type in the GUI replaces the global default only for that portal. Click "Reset to Default" in the GUI to go back to global settings.

🌐 Cross-Server Portals

Cross-server portals teleport the player to a different server in your BungeeCord or Velocity network. When a player steps through, the plugin:

Player enters portal
→
RabbitMQ sends coords to Server B
→
BungeeCord Connect → Server B
→
Player joins Server B → teleported to coords
Requirements for cross-server portals:
1. RabbitMQ must be configured and running.
2. BungeeCord/Velocity proxy must be running.
3. bungeecord: true must be set in spigot.yml on all servers.
4. The OreoEssentials plugin must be installed on ALL servers.
5. server-name in config.yml must match the proxy server name.

Setting up a cross-server portal

  1. Configure server-name on each server Open plugins/OreoEssentials/portals/config.yml on each server. Set server-name to match the server name in your proxy config. 
    # On your survival server:
server-name: "survival"

# On your lobby server:
server-name: "lobby"
  2. Select the region on Server A (survival) Use the wand or /portal pos1 / /portal pos2.
  3. Create with the destServer argument 
    /portal create to_lobby lobby 0 65 0 false lobby
    Format: /portal create <name> <destWorld> <x> <y> <z> [keepYaw] [destServer]
    Here destWorld is the world on Server B, and destServer is the server name.
  4. Test it Walk through the portal on Server A. You should be switched to Server B and arrive at the configured coordinates.
Timing note: The plugin sends the teleport destination via RabbitMQ 3 ticks before switching the player via BungeeCord. This gives Server B time to receive the destination before the player arrives. On slow networks, the destination is queued and applied when the player joins Server B.

🗺️ Warp Destination

Instead of hardcoded coordinates, you can set a portal's destination to a warp point managed by OreoEssentials' Warps module. This means if the warp location is updated later, the portal automatically uses the new location without needing to be edited.

Setting a warp destination via GUI

  1. Open /portal gui, click the portal.
  2. Click "Dest Warp". The GUI closes.
  3. Type the warp name in chat (e.g. spawn). If the warp doesn't exist you'll get an error and nothing changes. Type none to go back to using coordinates.
Warp destination takes priority over coordinates. When a portal has a destWarp set, the dest.x/y/z coordinates in portals.yml are ignored. If the warp is deleted later, players get an error message and cannot teleport through that portal until you fix the warp or clear the destWarp setting.

💬 Commands

The main command is /portal (alias: /portals).

CommandPermissionDescription
/portal wand oreo.portals.create Gives the selection wand. Left-click = POS1, right-click = POS2.
/portal pos1 oreo.portals.create Sets POS1 at your current location (no wand needed).
/portal pos2 oreo.portals.create Sets POS2 at your current location.
/portal create <name> <world> <x> <y> <z> [keepYaw] [server] [perm] oreo.portals.create Creates a portal from your current pos1/pos2 selection to the given destination.

❓ FAQ

Q: I created a portal but walking through it does nothing. Why?

Check these things in order:
1. Run /portal list — does the portal appear?
2. Run /portal info <name> — are the box coordinates correct?
3. Are you walking through the region, not just touching its border? The bounding box must fully contain your position (BoundingBox.contains()).
4. Is the Portals module enabled in OreoEssentials settings?
5. Check if you're on portal cooldown — the default is 1 second.

Q: The portal destination world doesn't exist on this server. How do cross-server portals save?

This is handled correctly — the plugin saves the original destination world name as a string in portals.yml regardless of whether that world is loaded. For cross-server portals the destination world lives on Server B, not Server A. When you edit other settings (like keepYawPitch) the world name is preserved.

Q: How do I change a portal's destination without deleting and recreating it?

Open /portal gui, click the portal, then click Set Dest Here. Your current location becomes the new destination instantly. All other settings (permission, particles, keepYawPitch) are preserved.

Q: Can two portals have the same name?

No. Portal names are unique and stored lowercase. Trying to create a second portal with the same name gives the error: "A portal with that name already exists".

Q: Can a portal's destination be in a different world on the same server?

Yes. When using /portal create, the <destWorld> argument can be any world loaded on the server. The portal region can be in world and the destination in world_nether, for example.

Q: I turned on ambient particles in config.yml but they don't show on any portal.

Each portal also needs ambient particles enabled per-portal via the Particles GUI (Ambient: DISABLED → click to enable). The global ambient-particles.enabled setting turns on the ambient task itself, but each portal has its own toggle. Enable both the global setting AND the per-portal toggle.

Q: How do I make a portal that sends players to a warp that might move later?

Use the Dest Warp feature. Open the GUI for the portal, click "Dest Warp", and type the warp name. The portal will always resolve the warp's current location at teleport time, so if the warp moves the portal automatically uses the new location.

Q: Can I have portals in different worlds at the same time?

Yes. Each portal stores its own world in portals.yml. The movement check (PlayerMoveEvent) compares the player's world to each portal's world before doing any bounding box check, so portals in other worlds are simply skipped.

Q: Is this compatible with Folia?

Yes. The plugin detects Folia automatically and switches to async teleportation. All tasks use OreScheduler which is Folia-aware. You can also manually set teleport-async: true in config.yml.

Q: I edited portals.yml manually but nothing changed.

The file is loaded into memory on startup. Manual edits are only picked up when you run /portal reload. Always reload after editing manually.
