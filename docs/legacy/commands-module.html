Module Documentation

Commands Module

Four powerful systems that control every aspect of how commands behave on your server. From creating entirely new commands out of YAML, to locking down what players can access, to triggering commands when a player right-clicks a block — it's all here.

aliases.yml Create any custom command out of thin air. Chain multiple commands, add conditions, cooldowns, costs, delays, and argument passing — all from YAML.
command-control.yml A firewall for commands. Choose between allowing everything by default (blacklist mode) or blocking everything by default (whitelist mode), with per-command permission gating.
commands-toggle.yml Turn any of OreoEssentials' built-in commands on or off. When disabled, the command is completely unregistered — players can't even see it in tab.
interactive-commands.yml Bind commands to blocks or entities in the world. When a player right-clicks them, the commands fire automatically — great for lobby buttons, NPCs, and signs.
aliases.yml

Custom Aliases — What They Are

An alias is a brand-new command you invent. You give it a name, write a list of real commands it should execute, and the plugin registers it as a real /yourcommand on the server. Players just type your command and the plugin runs everything behind the scenes.

Think of it like a macro. You could make a /kit starter that gives iron gear and food, a /daily that gives money every 24 hours, or a /wizard weather sun that changes the weather — all configurable entirely in YAML without touching any code.

File location: plugins/OreoEssentials/commandsmodule/aliases.yml
Aliases are registered as real Bukkit commands at startup and when you reload. Run /aliaseditor or /reloadall to pick up changes.
aliases.yml

All Alias Fields Explained

aliases:

  mycommand:                    # The command name — players type /mycommand
    enabled: true               # true = command exists; false = it's removed entirely
    run-as: PLAYER              # PLAYER (the player runs it) or CONSOLE (server runs it)
    cooldown-seconds: 60        # How many seconds before this player can use it again (0 = no limit)
    commands:                   # List of commands to run, in order
      - "give [playerName] diamond 1"
    checks: []                  # Alias-wide conditions (see Check Expressions section)
    logic: AND                  # AND = all checks must pass; OR = any one check is enough
    fail-message: "&cYou don't meet the requirements for /%alias%."  # Message if checks fail
    perm-gate: false            # true = player also needs oreo.alias.custom.mycommand
    add-tabs: false             # true = enable custom tab completion for this alias
    custom-tabs:                # Tab suggestions, one line per argument position
      - "option1,option2"       # These show up when the player presses Tab after /mycommand
FieldTypeDefaultWhat it does
enabledbooleantrueIf false, the command is skipped entirely — it won't be registered at all.
run-asPLAYER / CONSOLEPLAYERWho actually runs the commands. PLAYER means the player's own account runs them (useful for commands that check the caller's permissions). CONSOLE means the server's console runs them (useful for giving items or running admin commands without the player needing perms).
cooldown-secondsnumber0Per-player cooldown in seconds. 86400 = once per day, 3600 = once per hour. 0 means no cooldown.
commandslist of stringsemptyThe actual commands to run. Write them without the leading /. They run in order, top to bottom. Use inline directives (see next section) for advanced control.
checkslist of expressionsemptyConditions the player must meet to use this alias. If any check fails (with AND logic), the fail-message is shown and nothing runs.
logicAND / ORANDAND = ALL checks must pass. OR = at least one check must pass.
fail-messagestringbuilt-inMessage shown when alias-wide checks fail. Use %alias% to insert the command name. Supports & color codes.
perm-gatebooleanfalseIf true, player also needs the permission oreo.alias.custom.<name> in addition to the base use permission. Useful for VIP-only aliases.
add-tabsbooleanfalseIf true, the custom-tabs list is used to provide tab-completion suggestions.
custom-tabslist of stringsemptyEach line is a comma-separated list of suggestions for that argument position. Line 1 = suggestions for arg 1, line 2 = suggestions for arg 2, etc.

Inline Directives

Inline directives are special keywords you put at the very start of a command line (before the actual command text). They let you control how each individual line runs. You can stack multiple directives on a single line — they are stripped off in order.

DirectiveExampleWhat it does
asConsole! asConsole! give [playerName] diamond 1 Overrides the alias-level run-as for this one line only. The console runs this command, bypassing the player's permissions.
asPlayer! asPlayer! warp spawn Overrides the alias-level run-as for this line. The player themselves runs this command.
delay! <seconds> delay! 2 give [playerName] bread 5 Waits the specified number of seconds before running this command. The rest of the command list continues after the delay. Seconds are converted to ticks (×20). Decimals are supported (e.g. delay! 0.5).
cooldown:<seconds>?! cooldown:30?! feed [playerName] Per-line cooldown. If this specific line is still on cooldown for this player, the line is silently skipped and execution continues with the next line. The ?! suffix means "skip on cooldown" (the ! marks end of the directive value).
moneycost:<amount>?! moneycost:1000?! feed [playerName] Charges the player the specified amount via Vault before running this line. If the player doesn't have enough money, the line is silently skipped. The money is withdrawn before the command runs.
check:<expr>! check:$1==sun! asConsole! minecraft:weather clear 1d Per-line conditional. If the expression is false, this line is skipped and execution continues. Multiple check: directives on one line are all evaluated — all must pass (AND). See Check Expressions for the full expression syntax.
Stacking directives: You can combine them freely. For example:
check:$1==sun! moneycost:50?! cooldown:60?! asConsole! minecraft:weather clear 1d
This reads: "if the first argument is 'sun', and the player has $50, and this line isn't on a 60-second cooldown, run minecraft:weather clear 1d as console and charge $50."
aliases.yml

Variables in Command Lines

Inside command lines and check expressions, you can use these placeholders. They are replaced before the command is dispatched.

VariableReplaced with
[playerName]The name of the player who ran the alias.
$1, $2, $3…The arguments the player typed after the command. $1 = first word after the command, $2 = second word, etc.
$*All arguments joined together as a single space-separated string.
%papi_placeholder%Any PlaceholderAPI placeholder is resolved if PAPI is installed. Works in both command lines and check expressions.

Example using arguments

wizard:
  run-as: CONSOLE
  cooldown-seconds: 3
  commands:
    - "check:$1==weather! check:$2==sun! asConsole! minecraft:weather clear 1d"
    - "check:$1==day!   asConsole! minecraft:time set day"
    - "check:$1==night! asConsole! minecraft:time set midnight"
  add-tabs: true
  custom-tabs:
    - "weather,day,night"     # Tab suggestions when player types /wizard [TAB]
    - "sun,rain,thunder"      # Tab suggestions when player types /wizard weather [TAB]

With this config, typing /wizard weather sun will check if $1 == "weather" and $2 == "sun" — if both pass, it runs minecraft:weather clear 1d. Other lines are skipped because their checks don't match.

Check Expressions

Checks are conditions that must be true for the alias (or a specific line) to run. They live under checks: (alias-wide) or inline as check:<expr>!.

Permission checks

ExpressionPasses when…
permission:my.permissionThe player has my.permission.
!permission:my.permissionThe player does NOT have my.permission.

Numeric stat checks

ExpressionMeaning
money>=1000Player has at least $1000 (Vault balance).
level>=20Player is XP level 20 or higher.
exp>=500Player has 500 or more total XP points.

Comparison operators

OperatorMeaningExample
=Equals$1=sun
!=Not equals$1!=rain
>=Greater than or equal to (numeric)%player_health%>=10
<=Less than or equal to (numeric)level<=5
>Greater than (numeric)money>500
<Less than (numeric)level<10
<-Left string contains right%world%<-lobby
!<-Left does NOT contain right%world%!<-spawn
|-Left starts with right%world%|-world_
-|Left ends with right%world%-|_nether

On either side of the operator you can use $1…$n, PAPI placeholders like %auraskills_mana_int%, or literal values like 50 or "hello". Numeric comparisons work automatically when both sides parse as numbers.

command-control.yml

Command Control — What It Is

Command Control is a permission firewall that sits in front of every command on your server. When a player tries to run a command, this module decides whether to allow it or block it before Bukkit even sees it.

This is completely separate from Command Toggle (which removes OreoEssentials' own commands). Command Control can block any command from any plugin — /plugins, /version, even other plugins' admin commands.

Disabled by default. The module starts with enabled: false. You must set it to true and reload for it to take effect. A misconfigured DENY_ALL policy can lock players out of all commands — test carefully.
File: plugins/OreoEssentials/commandsmodule/command-control.yml
Bypass permission: oreo.commandcontrol.bypass — players with this skip all filtering.
command-control.yml

The Two Modes: ALLOW_ALL vs DENY_ALL

This is the most important choice. Think of it like a server firewall:

ALLOW_ALL (default/relaxed)
  • All commands are allowed unless specifically listed in blocked-commands.
  • Good for: servers where you just want to hide a few commands (like /plugins, /version).
  • Use blocked-commands to always-block specific roots.
DENY_ALL (strict/whitelist)
  • ALL commands are blocked unless you explicitly list them in allow-roots.
  • Good for: locked-down servers (minigames, lobbies) where players should only have a handful of commands.
  • Requires allow-roots to be fully configured or players can't do anything.
command-control.yml

All Fields Explained

command-control:
  enabled: false                  # Must be true to activate the module

  hide-from-tab: false            # true = blocked commands are also hidden from tab completion

  default-policy: "DENY_ALL"     # ALLOW_ALL or DENY_ALL (see section above)

  # When policy is DENY_ALL, these commands are allowed through (add more as needed):
  allow-roots:
    - "spawn"
    - "home"
    - "warp"
    - "ah"
    - "pay"

  # Require a specific permission to use a command root.
  # Format: commandname: "permission.node"
  # Even with ALLOW_ALL, the player needs this permission to use these commands.
  permission-map:
    fly: "oreo.commandcontrol.allow.fly"
    vanish: "oreo.commandcontrol.allow.vanish"

  # These are ALWAYS blocked, regardless of policy or permission-map.
  # Use this to hide sensitive commands universally.
  blocked-commands:
    - "plugins"
    - "pl"
    - "bukkit:plugins"
    - "version"
    - "ver"
    - "about"
    - "?"
    - "help"

  deny-message: "<red>You can't use that command.</red>"   # MiniMessage format

  # Advanced: per-command subcommand filtering (see Advanced Rules section)
  rules: []

How root normalization works

When the code reads a command, it normalizes the root before comparing:

  • Leading / is stripped.
  • Namespace prefix is stripped: minecraft:give → give.
  • Only the first word is used: give Steve diamond → give.
  • Everything is lowercased.

This means minecraft:give, /GIVE, and give all refer to the same root give.

command-control.yml

Advanced Rules — Subcommand Filtering

Rules let you allow or block specific subcommands under a root. For example, you could allow /lp but only permit user and group subcommands, blocking dangerous ones like editor. 

rules:
  - root: "lp"                      # Apply this rule to the /lp command
    mode: "ALLOW_ONLY"              # ALLOW_ONLY = whitelist subcommands; DENY_LIST = blacklist
    allow-empty: false              # true = allow /lp with no subcommand; false = block it
    permission-prefix: "oreo.lp."  # Optional: player needs oreo.lp.<subcommand> for each sub
    allow:                          # (used when mode is ALLOW_ONLY) — which subs are allowed
      - "user"
      - "group"
    deny:                           # (used when mode is DENY_LIST) — which subs are blocked
      - "editor"
      - "creategroup"
FieldDescription
rootThe command root this rule applies to (e.g. lp, gamemode).
modeALLOW_ONLY — only listed subcommands are allowed; everything else is blocked. DENY_LIST — only listed subcommands are blocked; everything else is allowed.
allow-emptyWhether running the root command with no subcommand (e.g. just /lp) is allowed.
permission-prefixIf set, the player needs <prefix><subcommand> for each sub they try to run. E.g. prefix oreo.lp. + sub user → needs oreo.lp.user.
allowList of allowed subcommands (used with ALLOW_ONLY).
denyList of blocked subcommands (used with DENY_LIST).
command-control.yml

Tab Completion Hiding

When hide-from-tab: true, blocked commands are also removed from tab completion. Players won't see them when they press Tab. This works at three levels:

  • PlayerCommandSendEvent — removes from the initial command list sent to the client.
  • AsyncPlayerSendCommandsEvent (Brigadier/Paper) — removes from the Brigadier command tree, so even modern tab-complete doesn't show them.
  • TabCompleteEvent — filters suggestions on-the-fly as the player types.

Players with oreo.commandcontrol.bypass always see everything in tab.

commands-toggle.yml

Command Toggle — What It Is

Command Toggle lets you enable or disable any of OreoEssentials' own built-in commands. When you set a command to enabled: false, it is completely unregistered from Bukkit's command map at startup — it doesn't just block the command, it removes it as if the plugin never registered it.

You can also toggle commands at runtime using /commandtoggle disable <name> without restarting the server. The change is saved to the config file immediately.

File: plugins/OreoEssentials/commandsmodule/commands-toggle.yml
Commands not listed in this file are considered enabled by default. You only need to add entries for commands you want to disable.
commands-toggle.yml

Config Structure

# plugins/OreoEssentials/commandsmodule/commands-toggle.yml

# Message shown when a player tries to use a disabled command:
disabled-command-message: "&cThis command is currently disabled."

commands:
  spawn:
    enabled: true                 # Set to false to disable /spawn entirely
    aliases: ["hub", "lobby"]    # Also disables these aliases when the command is disabled

  rtp:
    enabled: false                # /rtp and all its aliases are completely removed
    aliases: ["wild", "randomtp", "wilderness", "random"]

  home:
    enabled: true
    aliases: ["h", "gohome", "myhome"]

When you set a command to enabled: false, the aliases listed under it are also blocked. A player trying to use any of those aliases will receive the disabled-command-message.

How it works technically

The service uses Java reflection to access Bukkit's internal SimpleCommandMap.knownCommands map and removes the command entry from it. This is equivalent to the command never having been registered. Re-enabling a command re-registers it from the cached reference.

Important: The unregister/re-register system only works for OreoEssentials' own commands (those registered as PluginCommand by this plugin). You cannot toggle commands from other plugins with this system — use command-control.yml for that.
commands-toggle.yml

The /commandtoggle Command

Requires permission: oreo.commandtoggle.admin

CommandWhat it does
/commandtoggle listShows all commands and their current enabled/disabled status in two groups.
/commandtoggle enable <cmd>Enables a command in-memory and saves to config. Re-registers the command live if it was previously unregistered.
/commandtoggle disable <cmd>Disables a command in-memory and saves to config. Unregisters it from Bukkit live.
/commandtoggle status <cmd>Shows whether a specific command is currently enabled or disabled.
/commandtoggle reloadRe-reads the config file and re-applies all toggles. Use this after editing the YAML manually.

Tab completion is supported — pressing Tab after /commandtoggle enable or /commandtoggle disable will show all command names from the config.

Players with oreo.commandtoggle.bypass can use disabled commands even if toggled off.

interactive-commands.yml

Interactive Commands — What They Are

Interactive Commands (ICs) let you bind a list of commands to a specific block or entity in your world. When a player right-clicks that block or entity, the commands fire automatically — no player interaction with the command bar required.

Use cases: lobby buttons, warp signs, NPC interactions, clicking a chest to open a shop, stepping on a pressure plate (via adjacent block), healing pads, etc.

File: plugins/OreoEssentials/commandsmodule/interactive-commands.yml
Reload with /ic reload. The file is auto-created with a demo entry if it doesn't exist.
interactive-commands.yml

Config Structure

# plugins/OreoEssentials/commandsmodule/interactive-commands.yml

ic:                             # Root section — all ICs must be under "ic:"

  healer:                       # Name of this IC (you choose the name)
    public: false               # false = block/entity coords are bound manually
                                # true  = players with oreo.ic.sign can place [ic:healer] signs
    cmds:                       # Commands to run when clicked (in order)
      - "asConsole! delay! 1 effect give [playerName] regeneration 5 1"
      - "asConsole! title [playerName] actionbar {\"text\":\"Healed!\",\"color\":\"green\"}"
    blocks:                     # List of bound block positions: world;x;y;z
      - "world;100;64;200"
    entities:                   # List of bound entity UUIDs
      - "11111111-2222-3333-4444-555555555555"

  warp:
    public: true                # A sign can trigger this
    cmds:
      - "asPlayer! warp $1"    # $1 = second line of the sign
    blocks: []                  # (empty = not bound to specific blocks, only signs)
    entities: []
FieldTypeDescription
publicbooleanIf true, players with oreo.ic.sign can create signs like [ic:warp] that trigger this IC. If false, only block coordinates or entity UUIDs registered by an admin can trigger it.
cmdslist of stringsCommands that run when the IC fires. See Directives section for asConsole!, asPlayer!, delay!.
blockslist of stringsBlock positions in world;x;y;z format. Right-clicking any of these blocks fires the IC.
entitieslist of UUIDsUUID strings of entities. Right-clicking any of these entities fires the IC.
interactive-commands.yml

Admin Setup with /ic

You rarely need to edit the YAML directly — the /ic command lets you set everything up in-game. Requires permission: oreo.ic.

Step-by-step: creating a new IC

1
Create the IC
/ic new healer — creates an empty IC named "healer" and saves it.
2
Bind a block
Look at the block you want to be the trigger, then run:
/ic addblock healer — binds the block you're looking at (up to 7 blocks away).
3
Or bind an entity
Look at the NPC or mob (up to ~7 blocks away), then run:
/ic addentity healer — binds the entity's UUID.
4
Add commands
/ic addcmd healer asConsole! effect give [playerName] regeneration 5 1
You can add as many commands as you need, one at a time.
5
Test it
Right-click the bound block or entity as a player — the commands should fire. Use /ic info healer to verify the setup.

All /ic subcommands

CommandWhat it does
/ic new <name>Creates a new empty IC. Nothing fires yet — you need to add blocks/entities and commands.
/ic addblock <name>Binds the block you're looking at (max 7 blocks). You can bind multiple blocks to the same IC.
/ic addentity <name>Binds the entity you're looking at (max ~7 blocks range). You can bind multiple entities.
/ic addcmd <name> <command…>Appends a command to the IC's command list. Write the command without a leading /. Supports all directives.
/ic public <name> <true|false>Sets whether this IC can be triggered by signs. When set to true, players with oreo.ic.sign can place [ic:<name>] signs.
/ic listLists all ICs with their block count, entity count, command count, and whether they're public.
/ic info <name>Shows detailed info: all bound blocks, entities, and the full command list with line numbers.
/ic reloadRe-reads the YAML file. Use after editing interactive-commands.yml manually.
interactive-commands.yml

Public Signs

If an IC has public: true, players with oreo.ic.sign can create signs that trigger it — without having to bind specific block coordinates. This is great for admin-placed warps, shops, or buttons where you don't want to hardcode positions.

How to place a public IC sign

Place a sign with this text on line 1:

Line 1:  [ic:warp]          ← the IC name in [ic:name] format
Line 2:  spawn              ← becomes $1 in the commands
Line 3:  (optional)         ← becomes $2
Line 4:  (optional)         ← becomes $3

When you finish placing the sign, the plugin checks if the IC exists and is public. If yes, the sign text is replaced with [IC] and the IC name (so it's clearly labelled), and the sign's block position is automatically added to the IC's block list. Right-clicking the sign fires the IC.

The IC's commands receive the sign's line 2 as $1, line 3 as $2, etc. For example, with the warp IC: asPlayer! warp $1 becomes asPlayer! warp spawn.

Example public IC for warps: 
warp:
  public: true
  cmds:
    - "asPlayer! warp $1"
    - "asConsole! title [playerName] actionbar {\"text\":\"Warping to $1\",\"color\":\"gold\"}"
  blocks: []
  entities: []
Any admin with oreo.ic.sign can now place [ic:warp] signs anywhere with any warp name on line 2 — no config file editing required.

Troubleshooting

ProblemLikely cause & fix
My alias doesn't exist after adding it to aliases.yml Aliases are registered at startup or on reload. Run /reloadall or use /aliaseditor to trigger re-registration. Check console for "[Aliases]" log lines — if the count didn't increase, there's a YAML parse error.
Alias command runs but says "Unknown command" The command inside commands: doesn't exist on the server. Check spelling and make sure the target plugin is loaded. If run-as: PLAYER, the player also needs permission for that command.
Alias cooldown doesn't reset after /reloadall Cooldowns are stored in memory — they are not persistent across reloads or restarts. This is by design. If you want to manually clear a cooldown, restart the server.
Command Control DENY_ALL locked everyone out If you accidentally blocked everything, you can still use console commands. Set enabled: false in command-control.yml from console using sed or editing the file directly, then /reloadall. Or give an admin oreo.commandcontrol.bypass first.
command-control.yml is enabled but commands still aren't blocked Make sure enabled: true is set. Also confirm the player doesn't have oreo.commandcontrol.bypass. Check that the root command name is spelled correctly (no leading /, no namespace).
/commandtoggle disable works but the command is still usable The player may have oreo.commandtoggle.bypass. Also note that only OreoEssentials' own PluginCommands can be unregistered — external plugin commands require command-control.yml instead.
IC doesn't fire when I click the block Check /ic info <name> to see if the block is bound. Make sure you're right-clicking, not left-clicking. Also check that the event isn't cancelled by another plugin (WorldGuard, etc.).
