Module Guide

📦 Orders / Market

The Orders module is a player-driven buy-request marketplace. Instead of players selling items (like an auction house), here players post requests to buy items and other players deliver those items for payment. Money is locked up-front as escrow so sellers are always guaranteed to be paid. Supports Vault money, OreoEssentials custom currencies, optional fees, and optional cross-server sync.

Escrow-first economy The buyer's money is reserved the moment they create an order. Sellers never get stiffed — payment is atomic.
Two storage backends SQLite for single-server setups (zero config). MongoDB for multi-server networks with real-time sync.
Custom item support Fully compatible with ItemsAdder, Nexo, and Oraxen — custom item IDs are stored and displayed in the GUI.

What Is This Module?

Think of it like a wanted board at a marketplace. A player walks up and posts a note: "I want 64 Iron Ingots. I'll pay 5 coins each." That player's money (5 × 64 = 320 coins) is locked in escrow immediately. Any other player who has iron ingots can walk up, deliver some or all of them, and receive payment on the spot.

This is different from a classic auction house where sellers list items for buyers to purchase. Here:

RoleActionPays / Receives
Requester (Buyer) Creates an order: "I want X of this item for Y price each". Escrow locked immediately. Pays escrow up front. Receives items delivered by fillers.
Filler (Seller) Browses the market, finds an order they can fill, delivers items from their inventory. Items taken from inventory. Receives currency payment instantly.

An order can be partially filled by multiple players over time. For example, a request for 1000 diamonds could be filled by 10 different players each delivering 100, each getting paid their share.

The Escrow Concept — Why It Matters

Escrow means the buyer's money is held by the system, not the buyer. When a player creates an order for 64 Iron Ingots at 5 coins each, 320 coins are withdrawn from their wallet immediately and stored in the order record.

This is important because:

  • A filler can deliver items and get paid right away — no waiting, no trust required.
  • If the buyer logs off, gets banned, or spends their money elsewhere, the escrow is already reserved — fillers are safe.
  • If the buyer cancels their order, the remaining escrow is refunded — only what has already been paid out to fillers is gone.
Partial fill example: Player A posts: "I want 100 Iron Ingots at 10 coins each." → 1000 coins locked.
Player B delivers 40 ingots → gets 400 coins. Escrow now 600 coins, remaining qty now 60.
Player C delivers 60 ingots → gets 600 coins. Escrow hits 0, order marked COMPLETED.
Player A receives all 100 ingots across two deliveries.

Storage — SQLite vs MongoDB

SQLite (default)

SQLite is a self-contained database stored in a single file: plugins/OreoEssentials/orders/orders.db. No database server required. It works out of the box on any server. All fill operations use BEGIN IMMEDIATE transactions so two players filling simultaneously cannot cause double-payment. 

storage:
  type: "sqlite"
    sqlite:
    file: "orders.db"  # relative to plugins/OreoEssentials/orders/
SQLite limitation: SQLite is a local file. It cannot be shared across multiple servers. If you have two servers and a player on Server A creates an order, players on Server B will not see it. Use MongoDB for cross-server setups.

MongoDB

MongoDB stores each order as a document in the collection you configure. All fill operations use an atomic aggregation pipeline with $cond to automatically set the order to COMPLETED when remaining quantity reaches zero. This ensures perfect consistency even with concurrent fills from multiple servers. 

storage:
  type: "mongodb"
    mongodb:
    collection: "oreo_orders"  # name of the MongoDB collection
Note: The MongoDB URI and database name come from the main config.yml of OreoEssentials, not from settings.yml. Make sure your MongoDB connection is configured there first.

FeatureSQLiteMongoDB

Cross-Server Mode

When enabled, orders created on one server are instantly visible on all other servers in your network. This requires MongoDB (shared data store) and RabbitMQ (real-time event bus). 

cross_server:
  enabled: true       # must ALSO have storage.type: "mongodb"
  exchange: "oreo.orders"  # RabbitMQ exchange name

What cross-server sync does

When a player on Server A creates, fills, or cancels an order:

1
The order is written to MongoDB (shared by all servers).
2
An OrderSyncPacket is sent via RabbitMQ on the oreo.orders exchange.
3
All other servers receive the packet and update their in-memory order cache immediately.
4
Any player on any server currently viewing the market GUI has their GUI refreshed automatically (debounced by live_refresh_debounce_ticks).

Stale event protection

Each order has a revision counter that increments on every write. If a cross-server update arrives with a revision equal to or lower than what is already cached locally, it is silently discarded. This prevents out-of-order RabbitMQ messages from rolling back an order state.

Requirement: cross_server.enabled: true does nothing without storage.type: "mongodb". SQLite is a local file and cannot be shared between servers. The plugin will not crash, but orders will not sync.

RabbitMQ credentials

The RabbitMQ host, port, username, and password are read from OreoEssentials' main config.yml, not from the orders settings. You only specify the exchange name here. Make sure RabbitMQ is working for the rest of OreoEssentials before enabling this.

Economy Settings

economy:
  allow_vault: true
  allow_custom_currencies: true
  default_currency: "money"
SettingWhat it does
allow_vault When true, players can pay with Vault economy (regular server money). The currency picker shows a gold ingot button labelled "Vault Money". Requires Vault + an economy plugin (EssentialsX, CMI, etc.) to be installed. Set to false if you want a custom-currency-only market.

Custom-currency-only market: Set allow_vault: false and allow_custom_currencies: true. Players can only pay with your custom currencies. Great for game-loop economies that shouldn't use regular money.

Limits

limits:
  max_active_orders_per_player: 10
  max_quantity_per_order: 100000
  min_unit_price: 0.01
SettingDefaultWhat it does
max_active_orders_per_player 10 The maximum number of ACTIVE (unfilled / uncancelled) orders a single player can have at one time. If a player tries to create an 11th order, they get the error message "You have reached the maximum number of active orders." Cancelled and completed orders do not count toward this limit.
max_quantity_per_order 100000 The maximum item quantity that can be requested in a single order. If a player types a quantity higher than this in the chat input, they get an error. Setting this low (e.g. 1000) prevents absurdly large orders that may be hard to fill.
min_unit_price 0.01 The minimum price per item allowed. A player cannot set a unit price lower than this. Prevents free orders (price = 0) which would give away money without purpose. Use 1.0 if you want whole-number minimums.

Fees

Fees are disabled by default. When enabled, they act as a money sink — a percentage of each transaction is removed from the economy permanently. This is useful for servers with inflation problems. 

fees:
  enabled: false

  # % of total escrow charged when creating an order (burns money, not returned).
  create_fee_percent: 0.0

  # % of the payout deducted when filling an order.
  fill_fee_percent: 0.0
SettingWho pays itExample (5%)
create_fee_percent The buyer (order creator) pays this on top of their escrow when creating an order. Buyer wants 100 items at 10 coins each = 1000 coins escrow.
With 5% fee: buyer pays 1000 + 50 = 1050 coins total. The 50 is burned (not returned on cancel).
fill_fee_percent The seller (filler) has this deducted from their payout. Seller fills 10 items at 10 coins each = 100 coins gross.
With 5% fee: seller receives 100 − 5 = 95 coins net. The 5 is burned.
Create fee and cancellation: The creation fee is charged at order creation time and is never refunded — even if the order is cancelled before any fill happens. Only the remaining escrow (the unitPrice × remainingQty portion) is refunded on cancel.

Fee example — fully configured

fees:
  enabled: true
  create_fee_percent: 2.0   # buyer pays 2% on top of escrow
  fill_fee_percent: 1.0     # seller receives 1% less

UI Settings

ui:
  live_refresh_debounce_ticks: 10

When a cross-server order event is received (a new order, a fill, or a cancel), the plugin wants to refresh the GUIs of all players currently browsing the market. However, if many events arrive in rapid succession (e.g. 5 orders filled in 2 seconds), refreshing the GUI 5 times is wasteful and causes flickering.

live_refresh_debounce_ticks controls how long the plugin waits after the last event before actually refreshing. If a new event arrives within that window, the timer resets. This means the GUI refreshes once after the burst of events, not once per event.

10 ticks = 0.5 seconds. This is a good default. Increase to 20–40 if your server has very frequent order activity and you want less GUI churn. Decrease to 2–5 for near-instant updates on quieter servers.

Creating an Order — Step by Step

This is the full multi-step flow a player goes through when they want to post a buy request. Understanding it helps you explain it to your players and troubleshoot issues.

1
Hold the item in your main hand. Open the market (/market) and click Create Order (writable book, slot 45). A 3-row confirmation GUI opens. The item in your hand is shown in the center with the note "This is the item buyers will deliver." Click the green wool to confirm, red wool to cancel.
2
Type the quantity in chat. The GUI closes. A chat message asks: "How many items do you want to buy? Type the amount in chat." Type a whole number between 1 and max_quantity_per_order. If you type an invalid number you can try again — the pending state is kept.
3
Pick a currency. A 3-row currency picker GUI opens automatically after you enter a valid quantity. You see a gold ingot for Vault money and sunflowers for each custom currency. Click the one you want to pay with.
4
Type the unit price in chat. Another chat prompt: "What is your unit price? Type the price in chat (CurrencyName)." Type a price per item (e.g. 5 or 1.50). Commas are accepted as decimal separators (e.g. 1,50). Must be at least min_unit_price.
5
Confirm and pay. A 3-row order summary GUI opens showing: item, quantity, unit price, currency, total escrow, creation fee (if enabled), and total you will pay. Click Confirm & Pay (lime wool) — escrow is withdrawn immediately. Click Cancel to go back to the browser without paying.
What happens after confirmation: The escrow is withdrawn → the order is saved to the database → the in-memory cache is updated → a cross-server event is published (if enabled) → all open market GUIs refresh. If the database write fails, the escrow is automatically refunded and an error message is shown. No money is ever permanently lost due to a database error.

What does "item matching" mean?

When a filler tries to deliver items, the plugin checks whether items in their inventory match the order's item. Matching is strict:

  • Material type must match exactly (e.g. DIAMOND_SWORD matches only diamond swords).
  • If the item has ItemMeta (custom name, enchantments, lore, etc.), the meta must also match exactly.
  • A plain item (no meta) matches any item of the same material regardless of amount.

This means enchanted items, renamed items, and custom items (ItemsAdder, Nexo, Oraxen) can all be ordered precisely.

Filling an Order — Step by Step

Filling means delivering items to fulfil someone else's buy request. Here is the exact flow:

1
Browse and select. Open /market. Each order shows as an item icon with lore: who requested it, what item, how many remaining, unit price, currency, and how much you earn per item. Click any order that is not yours to open the fill details GUI.
2
Click "Fill This Order." The details GUI closes. A chat message asks: "How many [max] items will you deliver? Type the amount in chat." Type a number between 1 and the order's remaining quantity.
3
Confirm the fill. A 3-row confirm GUI shows: item to deliver, quantity, what you will receive (net after fill fee if enabled). Click Confirm. The plugin immediately checks you have enough matching items in your inventory.
4
Transaction completes. Items are taken from your inventory → the database is updated atomically → you are paid → the items are delivered to the order requester (or queued if they're offline). A success message shows: "Delivered X items! You received Y coins."
You cannot fill your own orders. If you try, the fill is rejected. This prevents self-dealing.

What if the order was filled by someone else between when you opened it and when you confirmed?

The plugin performs an atomic fill in the database. If the remaining quantity is now less than what you asked for, the fill returns an "insufficient quantity" result, your items are returned to your inventory, and you see the message: "Not enough remaining quantity. The order was partially filled. Please refresh." The market browser then reopens so you can see the updated state.

Cancelling an Order

A player can cancel their own active orders from the My Orders GUI (accessible via the chest button in the browser, slot 46). Each order in My Orders shows an action label: "YOUR ORDER — Click to manage." Clicking it opens a cancel confirmation GUI.

What happens on cancel

1
The order is atomically marked as CANCELLED in the database (only the requester can cancel their own order — enforced in the query).
2
The remaining escrow is refunded to the requester's wallet. If 30 out of 100 items were already filled, only the escrow for the remaining 70 items is returned.
3
The order is removed from the in-memory cache on all servers. All open market GUIs refresh.
Creation fee is not refunded. If you had create_fee_percent > 0, that fee was burned at creation time and is not returned when cancelling. Only the pure escrow amount (unitPrice × remainingQty) is refunded.
If the refund deposit fails (rare, e.g. economy plugin error), the order is still cancelled but the player's money may be lost. A SEVERE log entry is printed: "REFUND FAILED for order X — manual intervention required!" This is logged so you can correct it manually.

Offline Delivery System

When a player's order is filled, the items need to be delivered to that player. But what if the requester is offline at the time of filling? The plugin does not drop the items on the ground or void them. Instead, it uses a pending delivery queue.

How it works

1
Filler fills an order. The requester is offline (or on another server).
2
A PendingDelivery record is saved to the database: player UUID, item data, quantity, order ID.
3
When the requester next joins any server, the OrdersJoinListener fires, reads all pending deliveries for that UUID, and gives them their items immediately on login.
4
If the player's inventory is full, items are dropped at their feet (never lost).
Cross-server deliveries: With MongoDB storage, pending deliveries are visible to all servers. If a player is on Server B when their order gets filled on Server A, they receive the items the next time they join any server in the network.

Custom Item Support (ItemsAdder / Nexo / Oraxen)

OreoEssentials auto-detects custom items from three popular item plugins. When a player creates an order holding a custom item, the plugin tries to resolve its custom ID. This ID is stored in the order and shown in GUI lore for extra clarity.

PluginDetection methodGUI lore label
ItemsAdder Calls CustomStack.byItemStack(item).getNamespacedID() via reflection. &d▶ ItemsAdder: namespace:item_id
Nexo Calls NexoItems.idFromItem(item) via reflection. &d▶ Nexo: item_id
Oraxen Calls OraxenItems.getIdByItem(item) via reflection. &d▶ Oraxen: item_id
Reflection-based, so no hard dependency: None of these plugins are required. The detection is done via Java reflection at runtime. If ItemsAdder is not installed, its detection silently fails and the order works as a plain vanilla item. If it is installed, the custom ID is automatically detected and stored.
Item matching for custom items: The actual item matching when a filler delivers items is still done by comparing the vanilla ItemStack.getItemMeta(). Custom item plugins typically encode their ID in the item's persistent data container, which is part of ItemMeta. So a filler must deliver the exact same custom item — not just the same vanilla material.

Frequently Asked Questions

Q: A player created an order but it does not appear in the browser. Why?

If the database write fails during order creation, the escrow is automatically refunded and the order is not created. Check the console for [Orders] createOrder: save() failed. This usually means a SQLite file permission issue or MongoDB connection problem. Enable debug: true for more detailed logs.

Q: A player delivered items but did not get paid.

Check console for [Orders] fillOrder: logs. If atomicFill returned failure, the items were returned to the filler's inventory automatically. If atomicFill succeeded but the currency deposit failed, there will be a warning in the console. Enable debug: true to trace exactly what happened.

Q: A player cancelled an order but did not get their money back.

Check console for REFUND FAILED. This is a rare error where the economy plugin rejected the deposit. It does not happen under normal conditions. Manually check the player's balance and top them up if needed.

Q: Can a player fill their own order?

No. The service explicitly rejects self-fills and returns a generic error. This is hardcoded.

Q: What happens if a player fills an order and the requester's inventory is full?

Items are dropped at the requester's feet using world.dropItemNaturally(). Items are never voided. If the requester is offline, items are queued in PendingDelivery and given on their next login. If their inventory is full on login, items are dropped at their feet.

Q: I increased max_active_orders_per_player but the limit did not change for existing players.

Run /order reload. The limit is read from config on every order creation attempt — it is not cached per-player. After reloading, the new limit applies immediately.

Q: Can I have both Vault and custom currencies in the same market?

Yes. Set both allow_vault: true and allow_custom_currencies: true. Each order is tied to one currency. Orders paid in coins and orders paid in vault money both appear in the same browser — the lore shows which currency each order uses.

Q: I enabled fees but existing orders still show no fee deduction.

Fees are calculated at the time of the action (creation or fill). Orders that already exist in the database are not retroactively affected. New orders created after you enable fees will have the fee applied.

Q: How do I completely clear all orders (wipe the market)?

SQLite: Stop the server. Delete plugins/OreoEssentials/orders/orders.db. Restart. A fresh empty database is created automatically.
MongoDB: Drop the oreo_orders collection (and oreo_pending_deliveries if it exists) from your MongoDB console. All servers will start with an empty cache after their next startup.

Q: Is there a GUI to manage orders as admin (cancel any order, etc.)?

Not currently. Admin actions (force-cancelling orders, adjusting escrow) must be done directly in the database. For SQLite, use a SQLite browser tool. For MongoDB, use MongoDB Compass or the shell.

Q: How many orders can be shown on one page of the browser?

The browse GUI is a 6-row chest (54 slots). The bottom row (slots 45–53) is reserved for navigation buttons. That leaves 45 slots (rows 1–5) for order listings — 45 orders per page. The next/previous page arrows handle overflow beyond that.
