Module — Player Warps

Player Warps

Player Warps let your players create their own public (or private) teleport points and share them with the rest of the server. Think of it like a player-run warp system — each player owns their warps, and other players can browse and teleport to them through a GUI or command. Warps survive server restarts and are stored in YAML or MongoDB.

Per-rank limitsControl how many warps each rank can create. VIPs get more, admins get unlimited.
Full access controlLock, whitelist, password-protect, or make warps public. Managers can help manage them.
Cross-serverWarps on other servers are routed automatically via RabbitMQ + BungeeCord.

What are Player Warps?

A player warp is a named teleport location that a player creates at their current position. Once created, it can be found by other players through /pw gui (a browsable GUI) or used directly with /pw <warpname>.

This is different from admin warps (like /warp spawn) — player warps are owned by normal players, and each player can only create a limited number of them based on their rank.

Real-world examples

  • Steve creates a warp called steve_shop at his player shop. Other players type /pw steve_shop to teleport there.
  • Alex (VIP rank) creates up to 5 warps — her base, farm, and three shops. Default players can only create 3.
  • Notch makes a private warp with a whitelist — only invited players can teleport to it.
  • Herobrine locks his warp — nobody can use it except himself and his managers.
  • Admin uses /pw addwarps Notch 10 to permanently grant Notch 10 extra warp slots as a reward.
Key concept: Warp names are per-player. Two different players can both have a warp named shop — they don't conflict because each warp is identified by both the owner's UUID and the name together.

Quick-start (4 steps)

1

Check the config

Open plugins/OreoEssentials/playerwarps/config.yml. Set the default warp limit and add per-rank overrides. See the Config section below.

2

Give permissions

Give players oe.pw.base (required to use any pw command) and oe.pw.set (required to create warps). See the full permissions table.

3

Create a warp in-game

Stand at the location you want to warp to, then type /pw set myshop. The warp is created at your exact position (including facing direction).

4

Use the warp

Type /pw myshop to teleport directly, or /pw gui to open the browseable GUI and click the warp.

config.yml — fully explained

This is the only config file for Player Warps. It lives at plugins/OreoEssentials/playerwarps/config.yml.

# ==================== Player Warps Configuration ====================
# Controls how many warps each player / rank can create.
# The plugin checks permissions in order and uses the highest value.

limit:
  default: 3     # All players who don't match any rank get 3 warps

  # Add per-rank overrides using the rank name as key:
  vip: 5
  mvp: 10
  admin: 50

How the limit field works

The limit section has one required key (default) and any number of rank names. Every key except default is treated as a rank name.

When a player tries to create a warp, the plugin does the following:

  1. Starts with limit.default as the base limit.
  2. For every rank key (e.g. vip, mvp, admin), checks if the player has the permission group.<rankname>.
  3. If they do, and that rank's limit is higher than the current value, the higher value wins.
  4. The highest matching value becomes the player's effective limit.

This means ranks are additive by highest value, not additive by sum. A player with both group.vip and group.mvp gets the mvp limit (10), not vip+mvp (15).

How does the plugin know a player's rank? It checks Bukkit permissions. LuckPerms automatically grants players the permission group.<primarygroup>. So if a player is in the vip group, they automatically have group.vip — no extra setup needed.

Full example config with all ranks

limit:
  default: 3      # Regular players: 3 warps
  member:  5      # /lp group member permission group.member → 5 warps
  vip:     10     # VIP players: 10 warps
  mvp:     20     # MVP players: 20 warps
  elite:   30     # Elite players: 30 warps
  staff:   50     # Staff: 50 warps
  admin:   100    # Admins: 100 warps
Unlimited warps for admins: Give admins the permission oe.pw.limit.bypass — they can create unlimited warps regardless of the config value.

How rank limits work — step by step

Let's trace exactly what happens when a player types /pw set myshop:

1

Does the player have oe.pw.base and oe.pw.set?

If not, they get a "no permission" message and nothing happens.

2

Is the warp name already taken by this player?

Warp names are unique per owner. If you already have a warp called myshop, the command fails. Different players can each have their own myshop.

3

Calculate the effective limit

Read limit.default from config. Scan all rank keys. For each rank key the player has group.<rank> permission for, take the higher value. Also add any admin-granted extra slots (from /pw addwarps).

4

Count existing warps

Query storage for all warps owned by this player's UUID. If the count is already at (or above) the effective limit, block creation.

5

Create and save

The warp is created with the player's current location (including yaw/pitch facing direction), saved to storage, and registered in the directory (if cross-server is enabled). Success message is sent.

Example: Steve, Alex, Notch, and Herobrine

Let's say your config.yml looks like this:

limit:
  default: 3
  vip:     10
  mvp:     25
  admin:   100

What Steve actually sees when he hits his limit

Steve has 3 warps already and tries to create a 4th:

Steve > /pw set myfarm ✗ You've reached your warp limit (3).

Steve would need to either delete an existing warp with /pw remove <warp>, or get a rank upgrade (VIP would give him 10 slots).

What Alex sees with her VIP rank

Alex currently has 3 warps. She creates 7 more (up to her limit of 10):

Alex > /pw set alexshop ✓ Created warp alexshop. Alex now has 4/10 warps.

What happens if Alex gets demoted from VIP?

Her 10 existing warps are not deleted. However, she will no longer be able to create new warps until she removes some (since she'd be over the default limit of 3). Her current warps stay in storage and remain accessible to other players unless she removes them herself.

Admin-granted extra slots

As an admin, you can grant individual players extra warp slots on top of their rank limit using /pw addwarps <player> <amount>. These extra slots are persisted to disk (in plugins/OreoEssentials/playerwarps-extra.yml) and survive server restarts.

Admin > /pw addwarps Steve 5 ✓ Added 5 extra warp slot(s) to Steve. Total extra: 5. Steve's effective limit is now: default(3) + extra(5) = 8 warps.
Admin > /pw addwarps Steve -3 ✓ Added -3 extra warp slot(s) to Steve. Total extra: 2. You can reduce extra slots by adding a negative number.
Extra slots stack on top of rank limit, not replace it. If Alex (VIP, limit 10) gets 5 extra slots, her total is 15. The extra slots are independent of rank changes.

The extra slots file

Extra slots are saved to plugins/OreoEssentials/playerwarps-extra.yml. It looks like this:

extra:
  069a79f4-44e9-4726-a5be-fca90e38aaf5: 5   # Notch UUID → 5 extra slots
  853c80ef-3c37-49fd-aa49-938b674adae6: 2   # Steve UUID → 2 extra slots

You can edit this file manually (restart or reload required) or use the command.

Commands — Create & Delete

Steve > /pw set stonefarm ✓ Created warp stonefarm.
Steve > /pw reset stonefarm ✓ Reset warp stonefarm to your current location. (moved the warp point, all other settings kept)
Steve > /pw remove stonefarm ✓ Removed warp stonefarm.

Commands — Whitelist

The whitelist lets you restrict who can use your warp. When enabled, only the owner, managers, bypass-permission holders, and explicitly whitelisted players can teleport to the warp.

CommandDescription
/pw whitelist enable <warp> Enables whitelist mode on your warp. Everyone not on the list (except owner/managers) gets blocked.
/pw whitelist disable <warp> Disables whitelist. Warp becomes public again (or respects lock if locked).
/pw whitelist set <warp> <player> Adds a player to the whitelist. Also auto-enables the whitelist. The player does not need to be online.
/pw whitelist remove <warp> <player> Removes a player from the whitelist.
/pw whitelist list <warp> Shows all whitelisted players and whether whitelist is currently enabled.

There is also a standalone command /pwwhitelist <add|remove> <warpname> <player> as a shortcut.

Example: Notch makes his base invite-only

Notch > /pw whitelist set notchbase Steve ✓ Added Steve to whitelist of notchbase. (Whitelist auto-enabled.)
Notch > /pw whitelist set notchbase Alex ✓ Added Alex to whitelist of notchbase.
Herobrine > /pw notchbase ✗ You don't have permission to use notchbase. (Herobrine is not on the whitelist)
Steve > /pw notchbase ✓ Teleported to warp notchbase. (Steve is on the whitelist)

How access is decided — the check chain

Every time a player tries to teleport to a warp, the following checks run in order. The first match wins and either grants or denies access.

1
Required permission check

If the warp has a required permission set in the directory (admin feature), the player must have it. If they don't, blocked immediately.

2
Owner check — always allowed

The warp's creator can always use their own warp, regardless of lock/whitelist/password settings.

3
Manager check — always allowed

Players listed as managers on the warp bypass lock and whitelist restrictions (but still need the password if one is set in the command, not in canUse).

4
Staff bypass — oe.pw.bypass.lock

Players with this permission bypass all lock and whitelist restrictions for every warp on the server. Intended for admins and moderators.

5
Lock check

If the warp is locked (/pw lock <warp> on), all players not matched above are blocked. The GUI shows "You CANNOT use this warp."

6
Whitelist check

If whitelist is enabled, the player must be on the list. If not, blocked. The GUI shows "You are NOT whitelisted."

7
Public — allowed

If none of the blocking checks fired, the warp is public and anyone can use it.

After the canUse() check passes, there is a separate cost check (Vault economy), and a separate password check before the actual teleport fires.

Lock system

Locking a warp closes it entirely to the public. Only the owner, managers, and players with oe.pw.bypass.lock can use a locked warp.

# Lock your warp (nobody can use it except you, managers, and admins):
/pw lock mywarp on

# Unlock it:
/pw lock mywarp off

# Toggle (switches between locked and unlocked):
/pw lock mywarp
Lock vs Whitelist: Lock completely blocks everyone not explicitly allowed. Whitelist allows specific players you choose. Use lock when a warp is under construction or private. Use whitelist when you want to invite specific friends.

Whitelist — detailed

The whitelist stores a set of UUIDs. Players on the list can use the warp; others are blocked (when whitelist mode is enabled). The whitelist has a flag — enabled/disabled — that is separate from whether players are on the list.

  • You can add players to the whitelist while it is disabled, and enable it later.
  • Disabling the whitelist does not clear it — re-enabling brings back all previously added players.
  • Adding a player with /pw whitelist set automatically enables the whitelist.
Offline players work. You can add players who are currently offline to the whitelist. The system only needs their name — it resolves the UUID from Bukkit's offline player cache.

Password protection

A password-protected warp requires others to supply the correct password to enter. The owner, managers, and players with oe.pw.bypass.password are never asked for a password.

Setting a password

Herobrine > /pw password darkcave supersecret123 ✓ Set password for darkcave.
Herobrine > /pw password darkcave off ✓ Cleared password for darkcave.

Using a password-protected warp

Steve > /pw darkcave ✗ Warp darkcave requires a password. Use: /pw use darkcave <password>
Steve > /pw use darkcave supersecret123 ✓ Teleported to warp darkcave.

In the GUI

When a player clicks a password-protected warp in /pw gui, the GUI closes and a chat prompt appears asking them to type the password. Typing cancel aborts. If they disconnect before typing, the prompt is automatically cleaned up.

Passwords are stored in plain text. Do not use a password that is also used elsewhere. The password is visible in storage (YAML / MongoDB) to anyone with file/database access.

Managers

Managers are trusted players who can co-manage a warp. They bypass lock and whitelist restrictions just like the owner. They cannot delete the warp or transfer ownership.

Adding and removing managers

Steve > /pw managers steveshop Alex ✓ Added Alex as manager of steveshop.
Steve > /pw managers steveshop Alex ✓ Removed Alex as manager of steveshop. (running the command with the same player toggles them off)
Steve > /pw managers steveshop Managers for warp steveshop: (none)

YAML storage

When storage is set to YAML (the default), all warps are saved in a single file: plugins/OreoEssentials/playerwarps.yml. This file is created automatically on first use.

File structure

playerwarps:
  # Each warp uses its ID as the key: "<ownerUUID>:<warpname>"
  "069a79f4-44e9-4726-a5be-fca90e38aaf5:stonefarm":
    owner:       "069a79f4-44e9-4726-a5be-fca90e38aaf5"
    name:        "stonefarm"
    world:       "world"
    x:           -420.5
    y:           64.0
    z:           88.0
    yaw:         -90.0   # Facing direction (0=south, 90=west, -90=east, 180=north)
    pitch:       0.0
    description: "Free stone and cobblestone!"
    category:    "farm"
    locked:      false
    cost:        0.0
    icon:        # Bukkit ItemStack serialization (set by /pw icon)
      type:      STONE
    whitelist:
      enabled:   false
      players:   []
    managers:    []
    password:    # null = no password

In-memory cache

YAML storage keeps all warps in a HashMap<String, PlayerWarp> in memory after loading. Every save(), delete(), and read operation is synchronized to be thread-safe. The file is written to disk on every save call.

Warps that fail to load

If a warp references a world that is not currently loaded (e.g. a resource world that was deleted), it is skipped on startup with a warning in the console. The warp data stays in the YAML file — it will load again if the world comes back. It is not deleted.

MongoDB storage

When OreoEssentials is configured to use MongoDB, warps are stored in a collection (default: <prefix>playerwarps). Each warp is one document. Two indexes are created automatically at startup:

  • Unique index on id — prevents duplicate warps.
  • Compound index on (owner, name) — fast lookup by owner+name.

Document structure

{
  "id":               "069a79f4-...:stonefarm",
  "owner":            "069a79f4-44e9-4726-a5be-fca90e38aaf5",
  "name":             "stonefarm",
  "world":            "world",
  "x": -420.5,  "y": 64.0,  "z": 88.0,
  "yaw": -90.0, "pitch": 0.0,
  "description":      "Free stone and cobblestone!",
  "category":         "farm",
  "locked":           false,
  "cost":             0.0,
  "icon":             { "type": "STONE" },   // Bukkit ItemStack serialised as document
  "whitelist_enabled": false,
  "whitelist_players": [],
  "managers":         [],
  "password":         null
}

Saves use upsert replaceOne — if the document with that id exists it is replaced, otherwise inserted. No partial updates.

Directory collection

When cross-server is enabled, a second collection (<prefix>playerwarps_directory) stores which server each warp lives on. This is separate from the warp data itself. Each document is:

{ "id": "069a79f4-...:stonefarm",  "server": "survival-1" }

Warp ID format

Every warp has an internal ID built as: <ownerUUID>:<warpname> — for example: 

069a79f4-44e9-4726-a5be-fca90e38aaf5:stonefarm

This ID is used as the primary key in both YAML and MongoDB. Because the UUID is part of the ID, two different players can both have a warp named stonefarm without conflict — their IDs are different.

Warp names are always stored and compared in lowercase. Typing /pw set StOneFaRm creates a warp with name stonefarm.

Warps after a server restart

This is one of the most common concerns. Here is what survives a restart:

DataYAMLMongoDBNotes
Warp location (x/y/z/yaw/pitch)✅✅Fully persisted.
Description, category, cost✅✅Fully persisted.
Lock, whitelist, password✅✅Fully persisted.
Icon (ItemStack)✅✅Saved as Bukkit serialized map.
Managers, whitelist players✅✅Stored as UUID lists.
Admin extra warp slots✅✅Saved in playerwarps-extra.yml.
Warps in unloaded worlds⚠️ Skipped⚠️ SkippedNot deleted, but won't load until world is available again.
Everything is saved immediately. Every change (create, delete, rename, edit metadata, lock, whitelist) triggers a synchronous save to disk/database. There is no "save on shutdown" — data is never in a dirty state.

Cross-server warps

If your network has multiple servers (e.g. survival-1, survival-2, creative), players can own warps on one server and have other players teleport to them from a different server.

How it works — step by step

  1. Alex (on survival-1) types /pw alexfarm which lives on survival-2.
  2. The plugin looks up which server alexfarm is on (from the directory).
  3. It sends a PlayerWarpTeleportRequestPacket via RabbitMQ to survival-2.
  4. Simultaneously, it uses BungeeCord plugin messaging to send Alex to survival-2.
  5. When Alex arrives on survival-2, the broker sees the pending warp and teleports her to the warp location.
Network requirement: Cross-server warps require RabbitMQ (for the teleport packet) AND BungeeCord/Velocity (for the server switch). If either is unavailable, it falls back to a local teleport attempt.
Timing: The broker waits 3 ticks after the player arrives before teleporting them. If the player is not yet online when the packet arrives (because the server switch hasn't completed), the teleport is queued until the player's next join event.

Directory system

The PlayerWarpDirectory is a separate component from storage. While storage holds the warp data (location, metadata), the directory maps each warp ID to its server name. Think of it as a routing table.

OperationWhat happens
Create warpRegistered in directory: warpId → serverName
Delete warpRemoved from directory.
Rename warpOld entry deleted, new entry created under new ID.
Transfer ownershipOld entry deleted, new entry created under new owner's UUID.
Teleport to warpDirectory queried for server name; compared to local server to decide local vs. cross-server.

If cross-server is disabled or the directory is null, all teleports are treated as local.

Browse GUI (/pw gui)

Opened with /pw gui (requires oe.pw.gui). Shows all warps on the server sorted alphabetically. Each warp is displayed as an item (either its custom icon, or an Ender Pearl by default).

What the item shows

  • Name: The warp's name in green.
  • Owner: The player who created it.
  • Category: If set (e.g. shop, pvp).
  • Description: Word-wrapped across multiple lore lines if set.
  • Cost: If the warp charges money per teleport.
  • Status: Shows Locked, Whitelist, or Public with an indicator of whether YOU can access it.
  • Protection: Shows Password if a password is set.

Clicking a warp

  • If the warp has no password → teleports immediately (subject to canUse/lock/whitelist).
  • If the warp has a password and you're not the owner/manager → GUI closes, chat prompt appears asking you to type the password.

Navigation

The GUI displays 36 warps per page (rows 1–4). Row 5 (row index 5) has Previous/Next arrow buttons at slots (5,2) and (5,6).

My Warps GUI (/pw mywarps)

Opened with /pw mywarps (requires oe.pw.mywarps). Shows only your own warps. Clicking a warp opens an edit menu where you can manage settings directly from the GUI without commands.

Frequently asked questions

I created a warp but after a restart it's gone — what happened?

Check the server console for warnings on startup. The most common cause is that the world the warp is in was not loaded at startup time. The warp data is still in the file/database but was skipped because Bukkit couldn't find the world. Once the world loads, the warp becomes available.

Two players both have a warp named "shop" — which one does /pw shop go to?

/pw shop (without specifying an owner) calls service.listAll() and takes the first alphabetical match by name. This means one player's shop will "shadow" the other. To avoid this, use the GUI (/pw gui) where all warps are listed, or use the owner-specific lookup from within the service. Advise players to use unique names for public warps.

Can players rename a warp without losing all its settings?

Yes. /pw rename <old> <new> copies all metadata (description, category, icon, whitelist, managers, password, lock, cost) to the new warp object before deleting the old one. Nothing is lost.

What happens if a player is on the whitelist but whitelist is disabled?

The warp is public — everyone can use it. The whitelist entries are still stored but inactive. Re-enabling with /pw whitelist enable restores the restriction immediately.

Can I use /pw set from console?

No. All warp creation/management commands require a player context (they need to know your location, or you need to be online to be the owner). Admin commands like /pw addwarps, /pw removeall, and /pw setowner can be run from console.

What happens to warp counts when I switch storage modes (YAML → MongoDB)?

Switching storage modes requires a manual migration — warps in the old storage are not automatically copied. If you switch from YAML to MongoDB, you must manually import the data. Create a backup of playerwarps.yml before switching.

Does /pw reset preserve the warp's description, icon, whitelist, etc.?

Yes. /pw reset only updates the location (x/y/z/yaw/pitch). All other settings (description, category, icon, lock, whitelist, managers, password, cost) are kept exactly as they were.

How do I make a "warp shop" where players pay per teleport?

  1. Create the warp: /pw set myshop
  2. Set a cost: /pw cost myshop 50 — visitors pay $50, you receive the money.
  3. Optionally set a description: /pw desc myshop Best prices on the server!
  4. Optionally set an icon: hold a Gold Nugget, type /pw icon myshop

The payment goes directly from the visitor's Vault balance to your Vault balance. You (the owner) always teleport for free.

What is the difference between /pw and /pw use?

/pw <warp> is a shortcut that works for any warp that doesn't require a password. If the warp has a password, it tells you to use /pw use <warp> <password> instead. The use subcommand is the explicit version that also accepts the password inline.

Can a warp be on a different world to the player?

Yes, absolutely. Warps store the world name. Local teleports handle cross-world teleportation automatically via Bukkit's teleport API. The world just needs to be loaded on the same server.

Why don't warps have a "public/private" toggle?

The lock system acts as the "private" flag. Lock your warp to make it private. Unlock it to make it public. The whitelist adds a middle ground: invite-only. These three states (public / whitelist / locked) cover all use cases.
